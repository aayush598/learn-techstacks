# Tracking User Behavior

A comprehensive guide to understanding how users interact with your SaaS product — from event tracking and property definitions to funnel analysis, retention curves, and cohort analysis. This is how solo founders turn raw usage data into product decisions.

---

## Part 1: The Fundamentals of User Behavior Tracking

### Why Track User Behavior?

As a solo founder, you can't:
- Watch every user interact with your product
- Ask every user why they didn't come back
- Be present at every moment of delight or frustration

User behavior tracking gives you a scalable way to understand what's happening, even when you're sleeping.

### The Data Hierarchy

```
                      ┌──────────────────────┐
                      │   Business Impact     │ ← Revenue, retention, growth
                      │   (Why it matters)    │
                      └──────────┬───────────┘
                                 │
                      ┌──────────▼───────────┐
                      │   Insights & Action   │ ← What to change, what to build
                      │   (What to do)        │
                      └──────────┬───────────┘
                                 │
                      ┌──────────▼───────────┐
                      │   Metrics & Analysis  │ ← Funnels, cohorts, trends
                      │   (How to measure)    │
                      └──────────┬───────────┘
                                 │
                      ┌──────────▼───────────┐
                      │   Raw Events & Data   │ ← Pageviews, clicks, API calls
                      │   (What happened)     │
                      └──────────────────────┘
```

### Events vs. Properties vs. Users

| Concept | Definition | Example |
|---------|------------|---------|
| Event | An action someone took | `Task Created` |
| Event Property | Context about the action | `task_type: 'bug'`, `priority: 'high'` |
| User Property | Attributes of the person | `plan: 'pro'`, `team_size: 5` |

**The relationship:**
- Events record what happened
- Properties describe how it happened
- User properties describe who it happened to

## Part 2: Event Tracking In Depth

### Types of Events

#### 1. Page Events (Pageviews)

Tracked automatically by most analytics tools. Record when a user visits a page.

```javascript
// Automatic pageview tracking (PostHog)
posthog.capture('$pageview', {
  $current_url: 'https://app.yoursaas.com/dashboard',
  $pathname: '/dashboard',
  referrer: 'https://google.com'
});
```

**What to look for:**
- Which pages have highest drop-off?
- Which pages correlate with conversion?
- Traffic sources by page

#### 2. Click Events

Track specific user interactions.

```javascript
// Track button click
document.getElementById('export-report-btn').addEventListener('click', () => {
  analytics.track('Export Report Clicked', {
    export_format: 'pdf',
    report_type: 'monthly',
    page: currentPage
  });
});
```

#### 3. Custom Events (Business Logic)

Events you define that correspond to meaningful actions in your product.

```javascript
// Track core business event
function createTask(taskData) {
  // ... creation logic
  
  analytics.track('Task Created', {
    task_id: task.id,
    task_type: taskData.type,
    project_id: taskData.projectId,
    assignee_count: taskData.assignees.length,
    priority: taskData.priority,
    due_date_set: !!taskData.dueDate,
    source: 'web_app'
  });
}
```

#### 4. System Events

Events generated by backend processes, not user actions.

```javascript
// Track automated email sent
analytics.track('Email Sent', {
  email_type: 'onboarding_day_3',
  user_id: user.id,
  template: 'welcome_series_2',
  delivered: true
});
```

### Event Tracking Checklist

Every event should answer:
1. **Who?** - Which user (user_id)
2. **What?** - Action taken (event name)
3. **When?** - Timestamp (auto-recorded)
4. **Where?** - Page/context (URL, screen)
5. **How?** - Device, browser, app version
6. **Why?** - Related context (properties)

### Event Volume Planning

Estimate your monthly events to choose the right tool/plan:

```
Monthly Events = (Active Users × Sessions per User × Events per Session)

Example:
1,000 active users
× 10 sessions per user per month
× 5 events per session
= 50,000 events per month
```

Factor in autocapture (would multiply by 10-50x) and pageviews (multiply by sessions).

## Part 3: Properties — The Context That Makes Events Useful

### Event Property Best Practices

#### 1. Properties Should Be Immutable

Properties should describe what happened at that moment, not what's currently true.

```javascript
// GOOD: Properties capture the state at the time of the event
analytics.track('Plan Upgraded', {
  from_plan: 'basic',
  to_plan: 'pro',
  price_difference: 30,
  upgrade_source: 'pricing_page'
});

// BAD: Mixing current state with historical event
analytics.track('Plan Upgraded', {
  current_plan: getCurrentPlan(), // This might change later
  current_mrr: getCurrentMRR()
});
```

#### 2. Property Types

| Type | Examples | Use Case |
|------|----------|----------|
| String | `'pro'`, `'bug'`, `'google.com'` | Categories, identifiers |
| Number | `5`, `30.00`, `100` | Counts, amounts, durations |
| Boolean | `true`, `false` | Yes/no flags |
| Array | `['feature_a', 'feature_b']` | Multiple selections |
| Object | `{key: 'value'}` | Complex structured data |
| Timestamp | `2024-01-15T10:30:00Z` | When something happened |

#### 3. Property Naming Conventions

```
Use snake_case:     task_type, team_size, is_active
Use descriptive names: plan_name (not pn), user_role (not ur)
Be consistent:     dont_mix_snake_and_camel
Avoid abbreviations: organization (not org), configuration (not config)
```

#### 4. Property Value Guidelines

```javascript
// GOOD: Enum values (limited, consistent set)
analytics.track('Task Created', {
  priority: 'high',  // 'low', 'medium', 'high', 'critical' — consistent values
  status: 'todo'     // 'todo', 'in_progress', 'done' — not 'to do', 'to-do'
});

// GOOD: Numeric values for aggregation
analytics.track('Task Created', {
  assignee_count: 3,
  estimated_hours: 8
});

// AVOID: Free-form text (hard to analyze)
analytics.track('Task Created', {
  title: 'Fix the thing'  // What can you aggregate here? Nothing.
});
```

### User Properties

These are attributes attached to the user profile that persist across sessions.

```javascript
// Set user properties (Amplitude)
amplitude.setUserProperties({
  plan_tier: 'pro',
  mrr: 49,
  signup_date: '2024-01-15',
  acquisition_channel: 'organic_search',
  team_size: 5,
  integrations_active: ['slack', 'github', 'jira'],
  features_used: ['tasks', 'projects', 'reports'],
  total_projects: 12,
  days_active: 45
});

// PostHog
posthog.people.set({
  plan_tier: 'pro',
  mrr: 49
});
```

**When to set user properties:**
- On signup (plan, source, date)
- On plan change (upgrade, downgrade)
- On key milestone (first core action, first export)
- Periodically (monthly usage recalculations)

## Part 4: Funnel Analysis

### What is a Funnel?

A funnel tracks users through a sequence of steps. It shows where users drop off and where they convert.

### Building Your First Funnel

**Step 1: Define the funnel steps**

```
Example: Trial → Paid Funnel
Step 1: Website Visit (100%)
Step 2: Signup Clicked (15%)
Step 3: Registration Completed (12%)
Step 4: Onboarding Started (10%)
Step 5: Core Action Performed (8%)
Step 6: Entered Payment Info (3%)
Step 7: Subscription Active (2.5%)
```

**Step 2: Measure conversion between each step**

```
Website Visit → Signup Clicked: 15% conversion (85% drop-off)
Signup Clicked → Registration: 80% conversion (20% drop-off)
Registration → Onboarding: 83% conversion (17% drop-off)
Onboarding → Core Action: 80% conversion (20% drop-off)
Core Action → Payment Info: 37.5% conversion (62.5% drop-off)
Payment Info → Active: 83% conversion (17% drop-off)
```

**Step 3: Identify biggest drop-off points**

In this funnel:
- Biggest absolute drop-off: Website Visit → Signup Clicked (85% of all visitors)
- Biggest relative drop-off: Core Action → Payment Info (62.5% of activated users)
- Quickest win: Improving the post-activation conversion

### Funnel Types for SaaS

#### Acquisition Funnel

```
Visit → Signup → Activate → Retain → Refer
```

Used to understand your marketing and onboarding effectiveness.

#### Activation Funnel

```
Signup → Profile Setup → First Integration → First Core Action → First Export
```

Used to identify where users get stuck in their first experience.

#### Engagement Funnel

```
Login → Dashboard → Core Action → Collaborate → Return
```

Used to understand daily/weekly usage patterns.

#### Upgrade Funnel

```
On Free Tier → Hit Usage Limit → View Pricing → Compare Plans → Upgrade
```

Used to understand what drives conversion to paid.

#### Feature Adoption Funnel

```
Heard About Feature → Saw Feature → Tried Feature → Used Feature Again → Feature Becomes Habit
```

Used to understand if new features are being discovered and adopted.

### Analyzing Funnels

#### Step 1: Find the Drop-off

Look for steps with > 20% drop-off. Those are your biggest opportunities.

```
Funnel: Activation
Step 1: Signup → Profile Setup: 85% ✓
Step 2: Profile → First Integration: 62% ← HIGH DROP-OFF (38%)
Step 3: Integration → Core Action: 78%
Step 4: Core Action → Export: 90%
```

**Action:** Investigate why 38% of users who set up a profile don't connect an integration.

#### Step 2: Segment the Funnel

Break down the funnel by user segments:

```
Segment: By Acquisition Channel

Channel       | Signup → Setup | Setup → Integration | Integration → Core Action
Organic       | 88%            | 68%                | 82%
Google Ads    | 82%            | 52%                | 72%
Referral      | 92%            | 78%                | 88%
Twitter/X     | 78%            | 45%                | 68%
```

**Insight:** Google Ads and Twitter/X users struggle more with integration setup. They may need better onboarding tailored to their expectations.

#### Step 3: Time-Box the Funnel

Add time constraints:

```
"Users who connect an integration within 7 days of signup"
vs.
"Users who connect an integration at any time"
```

If time-constrained conversion is much lower, users need more guidance early on.

#### Step 4: Run Experiments

For the biggest drop-off step, design an experiment:

```
Problem: 38% drop-off between Profile Setup and First Integration
Hypothesis: Users don't understand which integration to choose
Experiment: Add recommended integration based on user's role
Success Metric: Increase setup→integration conversion from 62% to 75%
Duration: 2 weeks
```

### Funnel Analysis in Code

```python
# Pseudocode for funnel analysis
def analyze_funnel(events, funnel_steps, time_period_days=30):
    results = {}
    
    for i, step in enumerate(funnel_steps):
        users_here = get_users_who_did_event(events, step, time_period_days)
        
        if i == 0:
            results[step] = {
                'users': len(users_here),
                'conversion': 100.0,
                'dropoff': 0.0
            }
        else:
            prev_step = funnel_steps[i-1]
            prev_users = results[prev_step]['users']
            
            results[step] = {
                'users': len(users_here),
                'conversion': round(len(users_here) / prev_users * 100, 1),
                'dropoff': round(100 - (len(users_here) / prev_users * 100), 1)
            }
    
    return results
```

### Funnel Template (Google Sheets)

```

------------------------|---------|------------|----------|------------
Step 1: Visit Website   | 10,000  | 100%       | 0%       | 100%
Step 2: Signup Click    | 1,500   | 15%        | 85%      | 15%
Step 3: Signup Complete | 1,200   | 80%        | 20%      | 12%

**Formula:**
```

Drop-off = 1 - Conversion
Cumulative = Current_Entered / First_Entered
```

## Part 5: Retention Curves

### What is a Retention Curve?

A retention curve shows what percentage of users return to your product over time. It's the most important chart in your analytics dashboard.

### The Three Shapes of Retention

```
Shape 1: Flat (Great Product)
Day 1: 60%
Day 7: 50%
Day 30: 45%
Day 90: 40%
→ Your product is habit-forming. Users keep coming back.

Shape 2: Declining then Flattening (Good Product)
Day 1: 50%
Day 7: 30%
Day 30: 20%
Day 90: 18%
→ Some users are hooked, most aren't. Common for B2B SaaS.

Shape 3: Continual Decline (Bad Product / No PMF)
Day 1: 40%
Day 7: 15%
Day 30: 5%
Day 90: 2%
→ Users try it but don't come back. You need product changes.
```

### How to Build a Retention Curve

#### Step 1: Define Your Cohorts

Group users by the week or month they signed up:

```
Cohort A: Users who signed up in January 2024
Cohort B: Users who signed up in February 2024
Cohort C: Users who signed up in March 2024
```

#### Step 2: Define "Returning"

What counts as "returning"? Options:
- Logged in at all (weakest signal)
- Performed core action (strong signal)
- Spent > 5 minutes in app (strong signal)

Choose the one that best matches your product's value.

#### Step 3: Calculate Retention for Each Period

```
Cohort A (January 2024 — 100 users)
Month 0: 100% (signup month — all 100 users)
Month 1: 45% (45 of 100 returned in Feb)
Month 2: 38% (38 of 100 returned in Mar)
Month 3: 35% (returned in Apr)
Month 6: 30% (returned in Jul)
Month 12: 25% (returned in Jan 2025)
```

#### Step 4: Plot the Curve

```

### Benchmarks for B2B SaaS Retention

| Time Period | Good | Great | World-Class |
|-------------|------|-------|-------------|
| Day 1 | 40%+ | 60%+ | 80%+ |
| Week 1 | 30%+ | 50%+ | 70%+ |
| Month 1 | 20%+ | 40%+ | 60%+ |
| Month 3 | 15%+ | 30%+ | 50%+ |
| Month 6 | 10%+ | 25%+ | 40%+ |
| Month 12 | 8%+ | 20%+ | 35%+ |

### The "Smile" Curve

A product-market fit signal: when your retention curve starts to flatten and even slightly rise for later periods. This means power users are becoming more engaged over time.

```
Smile Curve Shape:
M1: 40% → M2: 32% → M3: 28% → M6: 30% → M12: 35%
```

This is rare and usually happens when:
1. Users invest data in your product (more data = more lock-in)
2. Network effects kick in (more users = more value)
3. Learning curve pays off (product gets more valuable with expertise)

### Retention Analysis in SQL

```sql
WITH user_first_action AS (
  SELECT 
    user_id,
    DATE_TRUNC('month', MIN(event_time)) AS cohort_month
  FROM events
  WHERE event_name = 'User Signed Up'
  GROUP BY user_id
),
monthly_activity AS (
  SELECT 
    u.user_id,
    u.cohort_month,
    DATE_TRUNC('month', e.event_time) AS activity_month
  FROM user_first_action u
  JOIN events e ON u.user_id = e.user_id
  WHERE e.event_name = 'Core Action'
  GROUP BY u.user_id, u.cohort_month, DATE_TRUNC('month', e.event_time)
),
cohort_sizes AS (
  SELECT 
    cohort_month,
    COUNT(DISTINCT user_id) AS cohort_size
  FROM user_first_action
  GROUP BY cohort_month
),
retention AS (
  SELECT 
    m.cohort_month,
    m.activity_month,
    COUNT(DISTINCT m.user_id) AS active_users,
    c.cohort_size,
    ROUND(COUNT(DISTINCT m.user_id) * 100.0 / c.cohort_size, 1) AS retention_rate
  FROM monthly_activity m
  JOIN cohort_sizes c ON m.cohort_month = c.cohort_month
  GROUP BY m.cohort_month, m.activity_month, c.cohort_size
)
SELECT 
  cohort_month,
  activity_month,
  retention_rate
FROM retention
ORDER BY cohort_month, activity_month;
```

## Part 6: Cohort Analysis

### What is Cohort Analysis?

Cohort analysis groups users by a shared characteristic and tracks their behavior over time. Unlike retention curves that focus on one metric, cohort analysis can examine any metric by group.

### Types of Cohorts

#### 1. Acquisition Cohorts (by signup date)

Group users by when they signed up. Most common cohort type.

```
Question: Are users who signed up this quarter more engaged than last quarter?
```

#### 2. Behavioral Cohorts (by action taken)

Group users by what they did.

```
Question: Do users who connect an integration in the first week retain better?
```

Example:
```
Cohort: Users who integrated in first 7 days
M1 Retention: 72%
M3 Retention: 58%

Cohort: Users who did NOT integrate in first 7 days
M1 Retention: 35%
M3 Retention: 22%
```

#### 3. Channel Cohorts (by acquisition source)

Group users by where they came from.

```
Question: Do organic users convert better than paid users?

Channel    | Signup→Trial | Trial→Paid | 90-Day Retention
Organic    | 85%          | 22%        | 38%
Google Ads | 78%          | 18%        | 28%
Referral   | 92%          | 35%        | 52%
```

#### 4. Feature Cohorts (by feature usage)

Group users by which features they use.

```
Question: Do users who use the reporting feature have higher LTV?

With Reports: LTV = $1,200, Churn = 2.8%
Without Reports: LTV = $600, Churn = 5.2%
```

#### 5. Plan Cohorts (by pricing tier)

Group users by which plan they're on.

```
Question: Are enterprise users retaining better than self-serve?

Enterprise: 12-month retention = 92%
Pro: 12-month retention = 68%
Basic: 12-month retention = 52%
```

## Part 7: Advanced User Behavior Analysis

### Path Analysis (User Flows)

Understand the sequence of actions users take.

**What to look for:**
- Common paths to activation
- Dead ends (users who get stuck)
- Unexpected behaviors (users using your product differently than you designed)

**Example path:**
```
Signup → Dashboard → Settings → Integrations → Slack → Create Task
                         ↘ Billing → Cancel
```

If 15% of users go from Dashboard to Billing to Cancel, your pricing page may be driving cancellations.

### Session Recording Review

Session recordings (available in PostHog, FullStory, Hotjar) let you watch real user sessions.

**Review protocol for solo founders:**

```
Weekly Session Review (30 minutes):
1. Watch 5 session recordings of:
   - 2 new users (first session)
   - 2 struggling users (high error rate or long pauses)
   - 1 power user (high engagement)

2. Take notes on:
   - Where did they hesitate? (mouse movement, long pauses)
   - Where did they make errors? (clicking wrong things)
   - What did they try that doesn't exist? (feature requests)
   - What delighted them? (positive reactions)
```

### Heatmap Analysis

Heatmaps show where users click, move, and scroll. Most useful for:
- Landing pages (what are people clicking?)
- Pricing pages (which plan gets most attention?)
- Dashboard (are users finding key actions?)
- Documentation (what are people searching for?)

### Event Correlation Analysis

Find which events predict positive outcomes:

```
Goal: User converts to paid within 30 days

Correlating events:
- Integration connected: 3.2x more likely to convert
- Team member invited: 2.8x more likely to convert
- First export: 2.1x more likely to convert
- Dashboard viewed: 1.4x more likely to convert
- Pricing page visited: 0.8x LESS likely to convert
```

**Insight:** Focus on getting users to connect an integration or invite team members — these are the strongest conversion predictors.

### Power User Analysis

Identify what makes your most engaged users different.

```
Power User Definition: Top 10% by core action frequency

Power User Characteristics:
1. 85% connected an integration in first week
2. 72% invited a team member in first month
3. Average time to first core action: 4 minutes
4. 90% completed onboarding in one session

Non-Power User Characteristics:
1. 22% connected an integration ever
2. 15% invited a team member ever
3. Average time to first core action: 3 days
4. 30% completed onboarding ever
```

**Action:** Build onboarding that mimics power user behavior — get all users to connect an integration and invite team members early.

## Part 8: Practical Implementation

### Setting Up Event Tracking in Your SaaS

```javascript
// analytics.js — Single file for all tracking
class Analytics {
  constructor() {
    this.initialized = false;
  }

  init(user) {
    if (typeof window.analytics === 'undefined') return;

    this.initialized = true;
    
    // Identify user
    window.analytics.identify(user.id, {
      email: user.email,
      name: user.name,
      plan: user.plan,
      signupDate: user.created_at,
      companySize: user.company_size,
    });
  }

  track(eventName, properties = {}) {
    if (!this.initialized) return;

    // Add standard properties
    const enrichedProperties = {
      ...properties,
      timestamp: new Date().toISOString(),
      url: window.location.href,
      app_version: APP_VERSION,
    };

    window.analytics.track(eventName, enrichedProperties);
  }

  // Specific event helpers
  trackSignup(method) {
    this.track('User Signed Up', { method });
  }

  trackCoreAction(actionType, projectId, details = {}) {
    this.track('Core Action Performed', {
      action_type: actionType,
      project_id: projectId,
      ...details,
    });
  }

  trackUpgrade(fromPlan, toPlan, source) {
    this.track('Plan Upgraded', {
      from_plan: fromPlan,
      to_plan: toPlan,
      upgrade_source: source,
      upgrade_date: new Date().toISOString(),
    });
  }

  trackCancel(reason, feedback) {
    this.track('Subscription Canceled', {
      reason_group: reason,
      feedback: feedback,
      days_as_customer: this.getDaysSinceSignup(),
    });
  }

  getDaysSinceSignup() {
    // Calculate from user object
    if (window.currentUser?.created_at) {
      const signupDate = new Date(window.currentUser.created_at);
      const today = new Date();
      return Math.floor((today - signupDate) / (1000 * 60 * 60 * 24));
    }
    return null;
  }
}

export const analytics = new Analytics();
```

### Data Quality Monitoring

Set up checks to ensure your tracking is reliable:

```sql
-- Check for missing events
SELECT 
  DATE(event_time) as date,
  event_name,
  COUNT(*) as event_count
FROM events
WHERE event_time > NOW() - INTERVAL '7 days'
GROUP BY DATE(event_time), event_name
ORDER BY date DESC, event_count DESC;

-- Check for null properties
SELECT 
  event_name,
  COUNT(*) as total,
  SUM(CASE WHEN properties->>'user_id' IS NULL THEN 1 ELSE 0 END) as missing_user_id
FROM events
WHERE event_time > NOW() - INTERVAL '24 hours'
GROUP BY event_name;
```

## Final Principles for Solo Founders

1. **Track 15 events, not 150.** Most of your insights will come from a handful of core events.

2. **Watch recordings, not dashboards.** One 10-minute session recording is worth 100 dashboard refreshes.

3. **Analyze cohorts, not aggregates.** "Average retention is 25%" tells you nothing. "Jan cohort retains at 30%, June cohort retains at 20%" tells you you're getting worse.

4. **Act on data within 48 hours.** An insight not acted on is trivia. When you see a problem in the data, take action before the data is stale.

5. **Qualitative > Quantitative for small sample sizes.** With < 100 customers, talk to them directly — your analytics won't have statistical significance.

6. **Track from day one.** You can't go back and capture events you didn't track. Even if you don't look at the data for months, you'll be glad you have it when you need it.
