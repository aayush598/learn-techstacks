# Solo Agile Framework

## Why Agile Still Matters When You're Alone

Agile methodologies were designed for teams, but the principles behind them are even more valuable for solo founders. Without a team to impose accountability, you need structure to:

- Maintain momentum when motivation dips
- Make progress on the right things
- Ship consistently
- Avoid rabbit holes and perfectionism
- Balance building with everything else (marketing, support, sales)

The solo agile framework adapts team-based agile practices for a single person. It gives you the benefits of structure without the overhead of meetings and coordination.

---

## 1. The Solo Agile Mindset

### The Core Principles Adapted for Solo

**Team agile principle → Solo adaptation**:

| Team Agile | Solo Agile |
|------------|------------|
| Daily standup meetings | Daily planning ritual |
| Sprint planning | Weekly priority setting |
| Backlog grooming | Feature idea management |
| Sprint review | Weekly accomplishment review |
| Retrospective | Self-reflection habit |
| Pair programming | Rubber duck debugging |
| Definition of done | Personal quality checklist |

### The Solo Agile Benefits

1. **Rhythm**: Consistent work patterns prevent burn-out and procrastination
2. **Focus**: Prioritization prevents building the wrong things
3. **Accountability**: Self-imposed deadlines create momentum
4. **Visibility**: Track progress and identify when you're stuck
5. **Adaptability**: Regular reflection helps you pivot when needed

### When You Don't Need Solo Agile

Solo agile isn't for everyone. Skip it if:
- You're still in exploration mode (no clear product direction)
- You're pre-revenue and need to try many things quickly
- You're building something simple that takes a week
- Structure feels suffocating rather than enabling

If you're past these early stages, solo agile will help you ship more consistently.

## 2. Personal Sprints

### The Weekly Sprint

For solo founders, the optimal sprint length is **one week**. Why?

- Short enough to stay focused
- Long enough to make meaningful progress
- Natural rhythm (Monday to Friday)
- Easy to plan (one week ahead)
- Quick feedback loop

### The Sprint Structure

```
Monday morning: Plan the week
  Review backlog → Set weekly goals → Break into tasks

Monday-Thursday: Execute
  Daily planning → Deep work blocks → Track progress

Friday afternoon: Review
  What shipped → What didn't → What to change

Friday/Saturday: Rest
  No work. Recharge.
```

### Sprint Capacity Planning

As a solo founder, you have approximately 40 hours/week total across ALL activities:

| Activity | Hours/Week | Notes |
|----------|------------|-------|
| Development | 20-25 | Product building |
| Marketing/sales | 5-10 | Content, outreach, sales calls |
| Support | 3-5 | User emails, bugs, questions |
| Operations | 2-3 | Billing, legal, accounting |
| Admin | 1-2 | Hiring, tools, compliance |
| Learning | 1-2 | Research, reading |

Your dev capacity for a week is roughly **20-25 hours**. Plan accordingly.

### Task Sizing

Break work into tasks that fit within 2-4 hours:

| Task Size | Hours | Examples |
|-----------|-------|----------|
| Tiny | 30 min - 1 hr | Fix CSS bug, update copy |
| Small | 1-3 hrs | Add form validation, create API endpoint |
| Medium | 3-6 hrs | Build new feature, write integration |
| Large | 6-12 hrs | New page, complex feature, major refactor |

A good week has:
- 1 medium task (6 hrs)
- 3-4 small tasks (8-12 hrs)
- 2-3 tiny tasks (2 hrs)
- Buffer for support/unexpected (4-5 hrs)

### Setting Sprint Goals

**Good weekly goal**: "Ship the CSV export feature"
**Bad weekly goal**: "Work on the analytics dashboard"

A goal should be:
- Specific: "What exactly will be done?"
- Measurable: "How do I know it's done?"
- Achievable: "Can I do this in 20-25 hours?"
- Relevant: "Does this move the needle?"
- Time-bound: "Done by Friday"

## 3. Backlog Management

### The Solo Backlog

Your backlog is all the things you COULD build. It doesn't need to be fancy—a simple list in your project management tool works.

### Backlog Structure

```
Backlog
├── Icebox (never, but keep for reference)
├── Someday (maybe in 6-12 months)
│   ├── Feature A
│   └── Feature B
├── Soon (next 1-3 months)
│   ├── Feature C
│   └── Improvement D
├── This month
│   ├── Feature E
│   └── Bug fixes
└── This week (current sprint)
    ├── Feature F (in progress)
    └── Task G (done today)
```

### Backlog Maintenance

**Weekly (15 min)**: Review and re-prioritize
**Monthly (30 min)**: Clean up stale items, add new ideas

Backlog rules for solo:
1. Maximum 20 items in "Soon" and above
2. If something hasn't moved in 3 months, move to Icebox
3. Only plan one week ahead (anything further is noise)
4. Remove, don't defer (if it's not important now, it might never be)

### Capturing Ideas

When inspiration strikes, capture it quickly:
- Use a note-taking app (Apple Notes, Notion, Obsidian)
- One line per idea
- Date it
- Review monthly

```
2024-03-15: Dark mode for dashboard
2024-03-12: CSV export with custom columns
2024-03-10: Team collaboration: shared workspaces
2024-03-08: Zapier integration for time tracking
```

## 4. Daily Planning

### The Daily Ritual (5 minutes)

Every morning:
1. **Check yesterday**: Did I finish what I planned?
2. **Set today's goal**: What's the ONE thing I must finish today?
3. **Block time**: When will I do the deep work?
4. **Check calendar**: Any meetings/calls I need to prep for?
5. **Note blockers**: What could stop me from making progress?

### The "One Thing" Principle

Each day, identify the ONE task that, if completed, makes the day a success. Everything else is bonus.

**Example**:
- One thing: "Complete the user import CSV parser"
- Other tasks: "Fix login bug", "Write blog post draft", "Respond to support emails"

If you only get the one thing done, it's a good day.

### Time Blocking

Instead of a to-do list, schedule your day:

```
9:00-9:30 - Daily planning, emails, support
9:30-11:30 - Deep work block 1 (main feature work)
11:30-12:00 - Quick tasks, email check
12:00-13:00 - Lunch, break
13:00-15:00 - Deep work block 2 (main feature work)
15:00-15:30 - Support, code review
15:30-16:30 - Shallow work (marketing, ops, learning)
16:30-17:00 - Wrap-up, plan tomorrow
```

### Handling Blockers

When you're stuck:
1. **Write down the problem**: Often the act of writing clarifies it
2. **Set a timer**: 25 minutes to try to solve it
3. **Move to something else**: If stuck after 25 min, switch tasks
4. **Come back fresh**: Next day with a clear mind
5. **Ask for help**: Twitter, forums, co-founder, friend

## 5. Velocity Tracking

### What Is Velocity

Velocity measures how much work you complete in a sprint. For solo founders, it's a simple metric: "How many tasks did I ship this week?"

### Tracking Your Velocity

Make a simple tracker:

```
Week 1: 8 tasks → 3 bugs, 2 features, 3 improvements
Week 2: 6 tasks → 1 feature, 3 bugs, 2 marketing tasks
Week 3: 10 tasks → 3 features, 4 improvements, 3 fixes
Week 4: 5 tasks → (holiday week, reduced capacity)
```

### What Velocity Tells You

1. **Your real capacity**: Not what you THINK you can do, but what you actually do
2. **Trends**: Are you improving, plateauing, or burning out?
3. **Accuracy**: How good are you at estimating? (Compare planned vs. actual)

### Improving Velocity

Why velocity might be low:
- Too many meetings/calls → Reduce commitments
- Too many small tasks → Batch similar tasks
- Perfectionism → Ship "good enough"
- Context switching → Time block deeper
- Burnout → Take more breaks, reduce hours

### Velocity Goals

Don't compare your velocity to anyone else's. Set personal goals:
- Current: 8 tasks/week
- Target: 10 tasks/week
- Stretch: 12 tasks/week

If you're consistently hitting your target, increase scope of tasks (tackle harder work). If you're consistently missing, reduce scope.

## 6. The Weekly Review

### The Review Structure (30 minutes every Friday)

**Part 1: What I shipped (10 min)**
List everything completed this week:
- Features built
- Bugs fixed
- Content published
- Support tickets resolved

**Part 2: What I didn't ship (5 min)**
What did I plan but not complete? Why?
- Underestimated complexity?
- Interrupted by support/emergencies?
- Lost motivation?
- Scope creep?

**Part 3: Key decisions (5 min)**
What decisions did I make this week that affect the product?
- Design decisions
- Technical choices
- Priority shifts

**Part 4: Next week plan (10 min)**
Set next week's goals:
- What MUST ship next week
- What WOULD BE NICE to ship
- Any known blockers

### The Monthly Review (1 hour)

First Friday of every month, do a deeper review:

**Product metrics**:
- New signups
- Active users
- Revenue
- Churn
- Feature adoption

**User feedback**:
- What are users saying?
- Top support requests
- Feature requests

**Big picture**:
- Am I building the right thing?
- Is the product direction correct?
- Do I need to change strategy?

## 7. The Retrospective

### Self-Retrospective Questions

Every two weeks, ask yourself:

1. **What went well?** (Keep doing this)
2. **What didn't go well?** (Stop or change this)
3. **What confused me?** (I need more clarity)
4. **What energizes me?** (Protect this)
5. **What drains me?** (Minimize this)
6. **What am I avoiding?** (Address this)
7. **What did I learn?** (Document this)

### Action Items from Retro

Turn insights into actions:

| Insight | Action |
|---------|--------|
| "I'm spending too much time on support" | Set 2 support windows per day |
| "I procrastinated on the billing feature" | Break into smaller tasks, start with easiest |
| "The feature I shipped got positive feedback" | Invest more in similar features |
| "I worked 60 hours and feel burnt out" | Set a hard stop at 6 PM |

### The Burnout Check

Include a burnout check in your retro:

- [ ] Am I sleeping 7+ hours?
- [ ] Am I exercising?
- [ ] Am I eating well?
- [ ] Am I taking weekends off?
- [ ] Do I still care about this product?
- [ ] Am I excited to work tomorrow?

If you answer "No" to 3+, take immediate action. Burnout kills more solo products than competition does.

## 8. Project Management Tools for Solo

### Tool Options

| Tool | Best For | Cost | Notes |
|------|----------|------|-------|
| **Linear** | Development-focused | Free team | Fast, keyboard-driven |
| **Notion** | All-in-one | Free | Flexible, can be heavy |
| **Todoist** | Task management | Free/paid | Simple, fast |
| **GitHub Projects** | Developer workflow | Free | Integrated with code |
| **Plane** | Open source Jira | Free | Self-hostable |
| **TickTick** | Task + time tracking | Free/paid | Good pomodoro integration |

### Recommended Setup

For most solo founders, a simple two-tool setup works:

1. **Notion** → Product roadmap, feature ideas, research notes
2. **Linear (or GitHub Projects)** → Weekly tasks, bugs, sprints

### The Solo Board Layout

```
┌─────────────┬──────────────┬──────────────┬────────────┐
│  Backlog    │  This Week   │  In Progress │  Done      │
├─────────────┼──────────────┼──────────────┼────────────┤
│ Feature A   │ Feature C    │ Feature B    │ Feature D  │
│ Feature E   │ Bug fix 1    │ (working on) │ Bug fix 2  │
│ Feature F   │ Improvement  │              │ Improvement│
│ Improvement │              │              │            │
└─────────────┴──────────────┴──────────────┴────────────┘
```

### The 15-Minute Weekly Setup

Every Monday morning:

1. Move items from "This Week" to "Done"
2. Archive old items from "Done"
3. Move top items from "Backlog" to "This Week"
4. Assign yourself to This Week items
5. Estimate each item (small, medium, large)
6. Go!

## 9. Definition of Done

### Why You Need a DoD

Without a Definition of Done, you'll:
- Ship features that almost work
- Create technical debt
- Miss edge cases
- Forget to update docs
- Get frustrated with your own incomplete work

### The Solo Definition of Done

For a feature to be DONE:

```
[ ] Code written
[ ] Tests written (unit + integration for critical paths)
[ ] Tested locally (functional check)
[ ] No console errors
[ ] Works on mobile (responsive check)
[ ] Accessible (quick axe check)
[ ] Error states handled (loading, empty, error, success)
[ ] Documentation updated (if applicable)
[ ] Deployed to production
[ ] Monitored for 24 hours (no errors)
```

### Task-Specific DoD

Adjust based on task type:

**Bug fix DoD**:
- [ ] Bug reproduced and verified
- [ ] Fix applied
- [ ] Test written to prevent regression
- [ ] Deployed and verified in production

**Feature DoD**:
- [ ] Code complete
- [ ] Tests pass
- [ ] Manual QA passed
- [ ] Works on Chrome/Firefox/Safari
- [ ] Accessible
- [ ] Deployed (behind feature flag if risky)

**Content DoD**:
- [ ] Written and reviewed
- [ ] Images/video included
- [ ] Links work
- [ ] SEO metadata set
- [ ] Published

## 10. Handling Interruptions

### Common Solo Interruptions

| Interruption | Frequency | Impact |
|-------------|-----------|--------|
| Support emails | Daily | Medium |
| User questions/calls | Weekly | High |
| Bug reports | Weekly | High |
| Social media | Daily | Low |
| Tool issues/outages | Monthly | Medium |
| Admin/legal | Monthly | High |
| Family/personal | Daily | Variable |

### The Interruption Budget

Plan for interruptions. Assume you'll lose 15-30% of your productive time to unexpected issues:

```
Planned capacity: 25 hours/week
Interruption buffer: 5 hours (20%)
Effective capacity: 20 hours/week
```

### Managing Interruptions

**Support windows**:
- Check support at 10 AM and 3 PM (not constantly)
- Respond to non-urgent issues within 24 hours
- Use auto-responders to set expectations

**Emergency protocol**:
1. Is this a P0? (All users affected, data loss, security)
2. If yes: Drop everything, fix it
3. If no: Schedule it for next support window

**Focus protection**:
- Close Slack, email, social media during deep work blocks
- Use "Focus mode" or "Do not disturb"
- Set status: "Working on [X]. Will respond after 2 PM."

## 11. Solo Agile Anti-Patterns

### Anti-Pattern 1: Working Without a Plan

"Just build stuff" without priorities. Everything feels equally important. Nothing ships.

**Fix**: Spend 15 minutes every Monday planning the week.

### Anti-Pattern 2: Overplanning

Spending hours perfecting the backlog, creating detailed specs, and color-coding tickets.

**Fix**: Plan one week ahead. One line per task. Ship before perfecting.

### Anti-Pattern 3: No Definition of Done

Shipping 80% complete features. Coming back to finish them later (but never doing it).

**Fix**: Write a 5-item DoD and stick to it.

### Anti-Pattern 4: Perfectionism

"I can't ship this until it's perfect." Result: nothing ships.

**Fix**: Ship "good enough" and iterate. Perfection is the enemy of shipped.

### Anti-Pattern 5: No Buffer

Planning 40 hours of work in a 25-hour-capacity week.

**Fix**: Assume 20-25 hours of effective dev time. Plan accordingly.

### Anti-Pattern 6: Never Reflecting

Shipping week after week without checking if you're building the right thing.

**Fix**: Weekly review. Monthly retrospective. Quarterly strategy check.

## 12. Solo Agile at Different Stages

### Pre-Product-Market Fit (0-10 users)

**Focus**: Speed of learning, not shipping features
**Cadence**: Weekly experiments, not sprints
**Process**: Minimal. Build → Test → Learn → Repeat

```
Monday: Choose one hypothesis to test
Monday-Thursday: Build the smallest test
Friday: Launch, measure, learn
Weekend: Analyze, decide next step
```

### Early Traction (10-100 users)

**Focus**: Activating users, improving retention
**Cadence**: Weekly sprints with 1-2 major goals
**Process**: Lightweight backlog, weekly review

```
Monday: Plan week (1 feature + fixes + improvements)
Monday-Thursday: Build
Friday: Ship, review metrics, plan next week
```

### Growth (100-1000 users)

**Focus**: Conversion, scaling, reliability
**Cadence**: Weekly sprints with defined scope
**Process**: Full solo agile framework

```
Full weekly sprint structure
Monthly retrospectives
Backlog management
Velocity tracking
```

### Scale (1000+ users)

**Focus**: Team building, delegation, systems
**Cadence**: Two-week sprints (if you have team members)
**Process**: Standard agile with team adaptations

```
When you hire, transition from solo agile to team agile
Each new person should learn your processes
Maintain the core principles of regular delivery
```

## 14. The Solo Agile Manifesto

1. **Ship weekly** — A week is a sprint. Ship something every week.
2. **Plan lightly** — 15 minutes for the week, 5 minutes for the day
3. **Prioritize ruthlessly** — One goal per week, one thing per day
4. **Track your velocity** — Know your real capacity, not your desired capacity
5. **Define done** — A checklist prevents half-shipped features
6. **Budget for interruptions** — Assume 20-30% time lost to unexpected work
7. **Review weekly** — What shipped, what didn't, what to change
8. **Rest intentionally** — Burnout doesn't help anyone
9. **Adapt the framework** — Solo agile serves you, not the other way around
10. **Ship before perfect** — A shipped feature is worth more than a perfect idea

Solo agile is not about following a rigid methodology. It's about creating enough structure to make consistent progress while maintaining the flexibility that makes solo building powerful. Start with the weekly sprint, add what works, and discard what doesn't.
