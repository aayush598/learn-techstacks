1. **What is API versioning and why is it needed?**
   - Changing the contract without breaking existing clients — consumers upgrade at their own pace, not when you redeploy.

2. **What are the main versioning strategies?**
   - URI versioning (/v1/users), query param (?v=1), custom header (X-API-Version), content negotiation (Accept: application/vnd.x.v1+json).

3. **What are the trade-offs of URI vs header versioning?**
   - URI: explicit, cacheable, universal support, but pollutes URLs. Header: cleaner URLs but invisible in logs and caches — choose by who consumes it.

4. **What is the difference between major and minor version changes?**
   - Major: breaking (field removal, behaviour change) — new version with migration path. Minor: additive (new fields, endpoints) — backwards compatible.

5. **What is the deprecation lifecycle?**
   - Announce -> mark Deprecated headers/Sunset -> serve both -> migrate users -> remove old version — with documented removals dates.

6. **What is default-versioning risk?**
   - Routing to a 'latest' version silently re-binds clients to future behaviour on deploy — pinning explicit versions avoids breakage surprises.

7. **How do you keep old versions alive cheaply?**
   - Version-specific route modules/blueprints, shared schemas where stable, and regression tests against the old contract — CI guards the transition.

8. **What does versioning mean for internal vs public APIs?**
   - Internal: aggressive change with coordinated deploys. Public: strict compatibility windows and long deprecation periods — trust capital.

9. **What is an API changelog?**
   - A documented list of what changed per version — clients plan upgrades; publishing one is the professional touch interviewers notice.

10. **How does GraphQL do versioning instead?**
   - Evolving schemas with deprecation directives rather than versioned endpoints — a philosophical advantage of schema-first contracts.
