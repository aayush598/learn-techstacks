1. **Design a rate limiter — what does it enforce?**
   - Max requests per unit time per client (e.g., 100/min per API key) — protecting the service from abuse and runaway clients.

2. **What are the classic algorithms?**
   - Token bucket, fixed window, sliding window log, and sliding window counter — each trades memory, accuracy, and burst tolerance.

3. **Explain token bucket.**
   - A bucket of tokens refilled at rate r, capacity b; a request consumes one token or is rejected — allows bounded bursts, simple, and the most common (used by APIs).

4. **What are the pros/cons of a fixed window?**
   - Simple counters per window — but the boundary spike: a client doubles its quota by straddling window edges.

5. **What is a sliding window counter?**
   - Weighting the current and previous windows by overlap — accurate near sliding-window with counter-only memory; the modern hybrid choice.

6. **Where does the limiter live?**
   - Client (weak), API gateway/server (request path), or a shared Redis layer (consistent across instances) — distributed enforcement needs a shared store.

7. **What happens to rejected requests?**
   - HTTP 429 with Retry-After header — clients back off instead of thundering again; distinguish from a client error by status codes.

8. **What is per-user vs global limiting?**
   - Per-key/tenant limits plus global caps protect against one tenant exhausting shared capacity — layered policy, not one rule.

9. **How do key expiry and memory work at scale?**
   - Redis hashes keyed by user+window with TTL; memory bound by active clients — a realistic cost model for millions of keys.

10. **How do you test a rate limiter?**
   - Burst, boundary-window, and distributed-consistency tests — under exact limits and overshoot, verifying the 429 path and retry semantics.
