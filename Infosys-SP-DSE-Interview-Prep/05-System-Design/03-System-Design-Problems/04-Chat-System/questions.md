# System Design Problems — Chat System Interview Questions and Answers

## Q1: Design a chat system — the core features?
**A:** One-to-one and group messaging, message persistence, delivery order, presence, and online/offline synchronisation — over WebSockets.

## Q2: What is the transport for real-time messages?
**A:** WebSockets for bidirectional push; REST for history/records; the connection is long-lived via load-balanced gateway endpoints.

## Q3: How do you store messages?
**A:** A messages table keyed by conversation_id with (sender, ts, content, status); Power-of-2-style chat isn't needed here — timestamp-ordering IDs are.

## Q4: How do you order messages correctly?
**A:** Server-assigned sequence numbers (or snowflake-style IDs) per conversation, applied at the server, not the client clock — network clocks lie.

## Q5: What happens to delivery when a user is offline?
**A:** Outbox/queue per user; on reconnect, sync missing messages since last_seq — the pull-on-reconnect pattern preserves ordering and durability.

## Q6: What is the read receipt / delivered model?
**A:** Delivery = pushed to gateway; read = user opened the conversation; both are separate status transitions recorded and broadcast.

## Q7: How do you scale WebSocket connections?
**A:** Stateless WebSocket gateways behind an LB (connection-sticky), presence tracked in Redis — rooms shard across gateways with pub/sub broadcasting.

## Q8: What is a pub/sub for chat rooms?
**A:** Redis pub/sub or Kafka per conversation fan-out: server sees one publish, sends to all connected members of that room — the broadcast primitive.

## Q9: What are the consistency vs availability trade-offs?
**A:** Online senders see others' messages via optimistic UI; offline sync reconciles — eventual consistency in ordering is acceptable and standard.

## Q10: How do you test a chat system?
**A:** Concurrent-message ordering, reconnection replay, and large-room fan-out load tests — plus presence flapping under network churn.
