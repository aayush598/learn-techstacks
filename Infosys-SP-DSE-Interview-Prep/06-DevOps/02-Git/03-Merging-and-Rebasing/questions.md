1. **What is merging in Git?**
   - Combining branches by creating a merge commit (or fast-forward) that reconciles the histories — history shows the branch topology.

2. **What is a merge conflict and how do you resolve it?**
   - Both branches changed the same lines — Git marks <<<<<<< / ======= / >>>>>>> blocks; you edit, decide, git add + commit the resolution.

3. **What is fast-forward merging?**
   - When the target branch hasn't moved, merging just moves its pointer forward — linear history without a merge commit; --no-ff forces a record instead.

4. **What is rebasing?**
   - Re-applying one branch's commits on top of another's tip — a clean linear history at the cost of rewritten commit IDs (never rebase shared history).

5. **What is the difference between merge and rebase?**
   - Merge preserves topology with a merge commit (safe for shared branches); rebase flattens into a linear story (clean, but rewrites order/IDs).

6. **What is cherry-picking?**
   - Applying a single commit from elsewhere onto the current branch without bringing the whole history — targeted hotfix transfer.

7. **What is git revert vs reset?**
   - revert creates an inverse commit (safe, keeps history, good for public branches); reset moves HEAD backwards discarding commits (rewrites — private/feature only).

8. **What is the golden rule of rebasing?**
   - Never rebase commits you've pushed/shared — rewriting public history breaks collaborators; revert instead on shared branches.

9. **How do you resolve a conflict during a rebase?**
   - Stop, edit conflicted files, git add, then git rebase --continue — or --abort to bail out; each step re-applies the next commit.

10. **What is an interactive rebase used for?**
   - git rebase -i lets you reorder, squash, fixup, or reword local commits — cleaning a messy feature branch before merge.

11. **What is squash merging?**
   - --squash collapses all feature commits into one on merge — concise history at the cost of loss of the detailed journey.
