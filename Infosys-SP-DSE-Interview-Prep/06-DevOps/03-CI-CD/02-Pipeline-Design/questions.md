# Ci Cd — Pipeline Design Interview Questions and Answers

## Q1: What is a CI/CD pipeline?
**A:** An automated series of stages: lint -> test -> build -> package -> deploy, run on every change — shipping small, verified increments.

## Q2: What are the stages of a typical pipeline?
**A:** 1) Checkout 2) Lint/format 3) Unit tests 4) Build artifacts/images 5) Integration/e2e 6) Deploy to env — each gate before promotion.

## Q3: What is the difference between CI and CD?
**A:** CI: integration/verification on every commit (tests, builds). CD: deployment automation after CI passes — continuous delivery (staged) vs continuous deployment (auto-prod).

## Q4: What are the top pipeline quality gates?
**A:** Lint, unit tests, coverage thresholds, dependency audit (pip-audit/dependabot), and image scanning — failing early is the point.

## Q5: How do you handle failing pipelines?
**A:** Fast feedback messages, flaky-test quarantining, and required-checks on merge — red pipelines are the team's canary, not a nuisance.

## Q6: What are environment promotion rules?
**A:** Dev -> staging -> prod with approvals at boundaries; secrets per environment; immutable versioned artifacts move up, not rebuilds.

## Q7: What is the difference between a build and a release?
**A:** Build: compiler/container artifact. Release: a tagged, immutable, deployable instance of a build (semver + changelog).

## Q8: What is trunk-based vs feature-branch CI?
**A:** Trunk: everyone merges to main frequently, CI runs on every commit — smaller diffs, less merge pain. Feature branches: longer-lived, larger merges.

## Q9: How do you make pipelines fast?
**A:** Caching, parallelism (independent stages), and only run the checks affected — CI velocity is the developer-experience metric.

## Q10: What is the value of pipeline-as-code?
**A:** Versioned YAML with reviewable diffs — configuration follows the same review/rollback discipline as application code.

## Q11: How would you pipeline a Python ML project?
**A:** Lint+pytest, train-validation step, model packaging, and a deploy step with model-version metadata — every step's artifacts tracked immutably.
