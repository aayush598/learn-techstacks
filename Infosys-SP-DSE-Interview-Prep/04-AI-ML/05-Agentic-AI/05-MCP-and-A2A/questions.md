1. **What is MCP (Model Context Protocol)?**
   - An open protocol standardising how LLM apps connect to tools/data sources — servers expose resources/tools/prompts; clients (agents/IDEs) consume them uniformly.

2. **How does MCP relate to function calling?**
   - Function calling is model-level; MCP is application-level — a uniform transport (stdio/HTTP) to expose tools as a service to any MCP-capable client.

3. **What are the MCP primitives — tools, resources, prompts?**
   - Tools: actionable functions the model may call. Resources: context/data retrievable (files, DB rows). Prompts: reusable instruction templates.

4. **What is the difference between a server and a client in MCP?**
   - The server exposes capabilities; the client (Claude Desktop, an agent framework, an editor) discovers and invokes them — decoupling tools from apps.

5. **What is A2A (Agent-to-Agent)?**
   - Google/community's Agent2Agent protocol defining deterministic contracts for agents to discover, negotiate, and cooperate across vendors.

6. **How do MCP and A2A differ in scope?**
   - MCP connects an agent to tools/data; A2A connects agents to other agents — the tool protocol vs the inter-op protocol distinction.

7. **Why standardise agent protocols?**
   - Every framework re-implementing tool wiring is waste; standards move the ecosystem — the engineering-economics argument interviewers respect.

8. **What would an MCP server for your project look like?**
   - Given MigratorGen/ScriptVector: an MCP server exposing 'migrate_script', 'semantic_search_snippet', 'run_analysis' as tools — pluggable into any client.

9. **What are the security considerations for MCP?**
   - Server provenance, tool permissions, and data exfiltration risks — least-privilege scoping per client; protocol adoption must include policy.

10. **What does the current MCP ecosystem baggage look like?**
   - Fast-moving, version churn, and client incompatibility — evaluate lock-in versus openness when choosing an agent stack.
