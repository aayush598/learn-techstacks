# Fastapi — Deployment Interview Questions and Answers

## Q1: How do you containerise a FastAPI app?
**A:** Dockerfile: python:3.11-slim, pip install from requirements, uvicorn command — multistage builds shrink image size for prod.

## Q2: What is the production run command for FastAPI?
**A:** gunicorn -w 4 -k uvicorn.workers.UvicornWorker app:app — multiple processes balancing async workers; or uvicorn directly for small apps.

## Q3: What is the .dockerignore / .env handling?
**A:** Exclude __pycache__, .venv, .env from the image; forward DATABASE_URL/SECRET_KEY via environment/compose — never bake secrets into images.

## Q4: What does the HEALTHCHECK endpoint do?
**A:** GET /health returning 200 when the app is up — used by load balancers and container orchestrators to decide instance health.

## Q5: How do you approach zero-downtime deploys?
**A:** Rolling updates (multiple instances restaged), readiness probes, and tagging immutable images — standard release engineering for APIs.

## Q6: What is uvicorn vs gunicorn vs daphne?
**A:** uvicorn: ASGI server (async). gunicorn: WSGI process manager wrapping uvicorn workers for CPU scaling. daphne: Django-specific ASGI.

## Q7: How do you manage environment configuration?
**A:** pydantic-settings BaseSettings reading env vars / .env files with typed defaults — config moving safely between dev/staging/prod.

## Q8: What is a reverse proxy + TLS termination?
**A:** nginx/traefik or a cloud LB terminates HTTPS and proxies to uvicorn on localhost — offloading certs and adding buffering.

## Q9: How do you set up CI/CD for the API?
**A:** GitHub Actions: run pytest + lint, build/push image, then deploy to the cluster/server on merge — the pipeline you listed on your resume.

## Q10: What metrics/logging do you ship?
**A:** Structured JSON logs via logging, request latency/error-rate metrics, and /metrics (Prometheus format) — observability prerequisites.

## Q11: How do you debug a crashed production instance?
**A:** Read structured logs, check health/readiness events, inspect resource metrics, reproduce locally with the same image/version — the SRE rundown.
