# Flask — Database Interview Questions and Answers

## Q1: What is Flask-SQLAlchemy?
**A:** The Flask extension wrapping SQLAlchemy with db = SQLAlchemy(app) — models subclass db.Model; sessions bound to request contexts.

## Q2: What is db.create_all vs migrations?
**A:** create_all builds tables from models (dev/tests only); Flask-Migrate (Alembic) version-migrates in production — never create_all against real data.

## Q3: How do you query in Flask-SQLAlchemy?
**A:** Model.query.filter_by(...).all(), .filter(Model.col == x), .order_by(desc(Model.date)), .limit(10).offset(0) — the CRUD query vocabulary.

## Q4: How do you insert/update/delete rows?
**A:** db.session.add(obj) / commit; obj.col = new; commit; db.session.delete(obj); commit — the ORM session/transaction unit.

## Q5: What is lazy loading in SQLAlchemy?
**A:** Relationships load on first access (default) unless eager_loaded with .options(joinedload(...)) — N+1 queries are the main SQLAlchemy perf trap.

## Q6: What is the N+1 query problem?
**A:** Loading N parents then accessing a relation issues N more queries; fix with selectinload/joinedload or explicit joins — a must-know ORM efficiency point.

## Q7: How do you write raw SQL alongside the ORM?
**A:** db.session.execute(text('SELECT ...')) for complex queries — the pragmatic escape hatch when the ORM abstracts too much.

## Q8: What is a backref and relationship?
**A:** db.relationship('Post', backref='author') gives two-way access Post.author and author.posts — concise relational mapping.

## Q9: How do you handle transactions in Flask?
**A:** Each request gets a session; commit at the end or rollback on 500; flask-shell propagates exceptions requiring explicit savepoints for partial success.

## Q10: What is the JSON column vs normalised tables?
**A:** JSON for flexible/semi-structured data; normalised tables for queryable relations — the schema-space trade-off in design discussions.
