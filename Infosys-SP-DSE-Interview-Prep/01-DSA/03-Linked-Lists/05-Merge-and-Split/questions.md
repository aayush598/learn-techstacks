# Linked Lists — Merge And Split Interview Questions and Answers

## Q1: State the recursion for merging two sorted linked lists.
**A:** Base: if one is None return the other. If l1.val<=l2.val, l1.next=merge(l1.next,l2), return l1; else symmetric. Tail-recursive but iterative version used often.

## Q2: How do you merge k sorted lists optimally?
**A:** Min-heap of k heads (O(log k) per pop/push) yields O(total log k). Better for interviews than merge-pairing (O(total log k) too but clunkier).

## Q3: How do you split an odd/even list (alternating nodes)?
**A:** Walk and attach each node to the appropriate odd/even list; truncate both tails. O(n).

## Q4: How do you split a singly list into halves cleanly?
**A:** slow/fast find middle, save second = slow.next, then slow.next=None to break. Handles even/odd lengths.

## Q5: How do you merge two lists alternately (zebra pattern)?
**A:** Interleave a1.next=a2head... with pointer advance through both; when one exhausts, attach the remainder. Used in 'merge in between' style.

## Q6: How do you merge sorted lists in place without allocating nodes?
**A:** Reuse existing nodes by relinking. Works because merge only reorders references; O(1) extra space beyond recursion.

## Q7: What is the 'merge two sorted lists' complexity?
**A:** O(n+m) time and O(max(recursion depth)) for recursive, O(1) extra space iterative. Both linear in input size.

## Q8: How do you partition a list into three groups (less/equal/greater)?
**A:** Three dummy-headed lists, per-node compare, then concat less+equal+greater avoiding null tails. Stable. O(n).

## Q9: How do you split a circular linked list into two without loss?
**A:** slow/fast to middle; cut at the point before slow; reconnect each cycle — both halves remain circular and whole.

## Q10: How do you merge two sorted lists of different lengths?
**A:** Two-pointer drains both; when one empties, attach the remaining tail of the other directly — no extra copying.

## Q11: What is the intuition behind the 05 merge and split technique used in coding interviews?
**A:** The core idea is to avoid brute force by exploiting structure: leftover wasted compares are removed, and each element is processed a small constant number of times, driving complexity down to an optimal bound that interviewers expect you to justify.

## Q12: Write the brute-force approach for a typical 05 merge and split problem and analyse it.
**A:** Brute force enumerates every candidate configuration, e.g., every subarray/combination/permutation, giving O(n^2), O(n^3) or O(2^n). It is correct but only useful for small inputs; the interview follow-up is to optimise it to linear or O(n log n).

## Q13: State the time and space complexity of the optimal solution for most 05 merge and split problems.
**A:** The optimal solution is usually O(n) time with O(n) space, or O(n) time with O(1) space when a monotonic/pointer trick applies. Always state constants and best/worst cases explicitly.

## Q14: What common edge cases must be handled in 05 merge and split implementations?
**A:** Empty input, single-element input, all-equal values, negative numbers, duplicates, off-by-one at the last index, and large values where intermediate sums/products can overflow — every one must be tested.

## Q15: How would you dry-run your 05 merge and split code on a small example in an interview?
**A:** Pick a tiny input, walk index by index while updating each variable, and show the invariants hold at every step. This proves both correctness and that you truly understand the algorithm, which Infosys interviewers probe by asking you to trace code by hand.

## Q16: Give a real-world analogy for 05 merge and split.
**A:** Analogy: 05 merge and split is like scanning a line of people for a specific property while remembering a few key facts — each person is visited once and relevant state is carried forward, exactly how the optimal solution behaves.

## Q17: How do you decide between a hash map, sorting, or two pointers as tools for 05 merge and split?
**A:** Hash map when you need membership/paired lookup in O(1) and space is affordable; sorting when order gives a monotonic advantage (two pointers, binary search); pointers directly when the input is already sorted. Trade space for speed only when constraints allow.

## Q18: What is the role of a prefix/suffix precomputation in 05 merge and split?
**A:** Precomputation turns repeated subcomputations into O(1) lookups, converting an O(n^2) nested loop into O(n). Common wherever the value at index i depends on an aggregate over a range around i.

## Q19: Explain the optimisation step you would mention after writing the naive version for 05 merge and split.
**A:** First remove redundant recomputation via memoisation or prefix arrays; next, exploit monotonicity with two pointers/sliding window; finally, reduce space by keeping running variables instead of full tables — always closing with the improved complexity.

**A:** In the assessment only correctness/speed of the final code matters and hidden tests matter; in the live round the interviewer wants your thought process, complexity analysis, edge cases, and a hand trace — both must be practiced.
