# Segment Trees And Fenwick — Range Queries Interview Questions and Answers

## Q1: What range queries are typical with segment trees?
**A:** Range sum, min/max, gcd/lcm, mode (with merge making it subtle), OR/AND/XOR, and kth-element find — all over ± static or updatable arrays.

## Q2: How do you handle range max with point updates?
**A:** Segment tree store max; query uses max as the combine; point update recomputes leaf then ancestors. O(log n) per op.

## Q3: How do you answer Range Minimum Query with a segment tree vs sparse table?
**A:** Segment tree supports updates and O(log n) queries; sparse table precomputes O(n log n) and answers RMQ in O(1) but no updates — choose by update presence.

## Q4: How does range GCD query work?
**A:** Store gcd at nodes; combine = math.gcd(l,r); query over the range with identity 0. O(log n). GCD properties survive the canonical decomposition.

## Q5: How do you handle range XOR queries?
**A:** XOR aggregate with identity 0 and segment-tree support; combined with lazy XOR lets you flip ranges quickly — used in advanced updates.

## Q6: How do you merge counts of elements within ranges (online, updates)?
**A:** Wavelet tree / merge-sort tree; or store per-node sorted buckets and answer count-in-range via binary search. O(log^2 n) query — a common extension.

## Q7: How do you combine segment-tree with DS like a Fenwick for 2D?
**A:** Fenwick of segment trees (or vice versa) answers 2D range updates/queries in O(log^2 n) — the nested-DS pattern for grid problems.

## Q8: What is the 'kth missing / kth-1 index' on a segment tree?
**A:** Walk the tree tracking how many elements lie left; descend left if accumulated+k ≤ left count else right — O(log n) 'find by order'. A classic descendant query.

## Q9: How do you compute prefix sums with a segment tree?
**A:** prefix(l) = query(1..l); or store each node's aggregate and navigate. Fenwick (BIT) does prefix sums faster, but segment tree is general.

## Q10: When is a sparse table better than a segment tree?
**A:** Immutable arrays needing O(1) RMQ — sparse table precomputes; for updates it's useless — segment tree wins.

## Q11: What is the intuition behind the 02 range queries technique used in coding interviews?
**A:** The core idea is to avoid brute force by exploiting structure: leftover wasted compares are removed, and each element is processed a small constant number of times, driving complexity down to an optimal bound that interviewers expect you to justify.

## Q12: Write the brute-force approach for a typical 02 range queries problem and analyse it.
**A:** Brute force enumerates every candidate configuration, e.g., every subarray/combination/permutation, giving O(n^2), O(n^3) or O(2^n). It is correct but only useful for small inputs; the interview follow-up is to optimise it to linear or O(n log n).

## Q13: State the time and space complexity of the optimal solution for most 02 range queries problems.
**A:** The optimal solution is usually O(n) time with O(n) space, or O(n) time with O(1) space when a monotonic/pointer trick applies. Always state constants and best/worst cases explicitly.

## Q14: What common edge cases must be handled in 02 range queries implementations?
**A:** Empty input, single-element input, all-equal values, negative numbers, duplicates, off-by-one at the last index, and large values where intermediate sums/products can overflow — every one must be tested.

## Q15: How would you dry-run your 02 range queries code on a small example in an interview?
**A:** Pick a tiny input, walk index by index while updating each variable, and show the invariants hold at every step. This proves both correctness and that you truly understand the algorithm, which Infosys interviewers probe by asking you to trace code by hand.

## Q16: Give a real-world analogy for 02 range queries.
**A:** Analogy: 02 range queries is like scanning a line of people for a specific property while remembering a few key facts — each person is visited once and relevant state is carried forward, exactly how the optimal solution behaves.

## Q17: How do you decide between a hash map, sorting, or two pointers as tools for 02 range queries?
**A:** Hash map when you need membership/paired lookup in O(1) and space is affordable; sorting when order gives a monotonic advantage (two pointers, binary search); pointers directly when the input is already sorted. Trade space for speed only when constraints allow.

## Q18: What is the role of a prefix/suffix precomputation in 02 range queries?
**A:** Precomputation turns repeated subcomputations into O(1) lookups, converting an O(n^2) nested loop into O(n). Common wherever the value at index i depends on an aggregate over a range around i.

## Q19: Explain the optimisation step you would mention after writing the naive version for 02 range queries.
**A:** First remove redundant recomputation via memoisation or prefix arrays; next, exploit monotonicity with two pointers/sliding window; finally, reduce space by keeping running variables instead of full tables — always closing with the improved complexity.
