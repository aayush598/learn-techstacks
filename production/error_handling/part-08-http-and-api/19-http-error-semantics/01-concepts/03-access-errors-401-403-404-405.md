# Access Errors — 401, 403, 404, 405

> Part VIII · Chapter 19 · Sections 19.3, 19.4, 19.5, 19.6 · _Estimated reading time: 18 min_
> **Prerequisite:** [Status Code Classes and Selection Table](./01-status-code-classes-and-selection-table.md)

## In one sentence

`401` answers "who are you?", `403` answers "may you do this?", `404` answers "is it here?",
and `405` answers "may you do it *this way*?" — and mixing any two of them leaks either
existence information or permission structure to the wrong caller.

## Why this matters in production

These four statuses sit on the hottest error paths in any SaaS API: every expired token, every
tenant-isolation mistake, every wrong route in a client. Getting them wrong has two concrete
costs. **Security cost:** returning `403` on a missing resource confirms to an attacker that
the resource exists (existence oracle); returning `404` on another tenant's project is usually
right — but returning `403` when you meant `401` teaches clients to treat "log in again" as
"access denied," silently trapping users in a broken session. **Support cost:** wrong statuses
turn every "why can't my user open this?" ticket into a debugging session across three layers
instead of one.

## Core concept — the two axes

The four statuses answer two independent questions, and they must be asked in order:

```text
        Axis 1: IDENTITY                Axis 2: PERMISSION / LOCATION
        ─────────────────               ──────────────────────────────
        Do we know who you are?         Do you get to touch this thing?
              │                                  │
   NO ────────┴──▶ 401 Unauthorized              ├── allowed ──▶ 2xx
   YES                                          ├── not allowed, but
                                                 │   it exists ──▶ 403 Forbidden
                                                 ├── not allowed, and
                                                 │   hidden ─────▶ 404 Not Found
                                                 └── doesn't exist ─▶ 404 / 410
```

- **`401 Unauthorized`** (RFC 9110) is historically misnamed: it means **unauthenticated**.
  No credentials, invalid credentials, expired token, bad signature. The RFC **requires** a
  `WWW-Authenticate` header on every `401`. The correct client action is to (re)authenticate,
  not to "fix permissions."
- **`403 Forbidden`** means the credentials are valid, the principal is known, and the request
  is **not allowed**: wrong role, another tenant's resource, suspended account, a fail-closed
  decision on an uncertain authz dependency. The client must not retry with the same
  credentials.
- **`404 Not Found`** means the target **is not there for this principal**. Note the hedge:
  for resources a user cannot even know exist, `404` is the *safe* answer whether the row is
  absent or merely owned by another tenant. `404` never confirms existence.
- **`405 Method Not Allowed`** means the **path exists** but this method does not. RFC 9110
  **requires** an `Allow` header listing the supported methods. `405` on a nonexistent path is
  wrong — an unknown path is `404`.

> RFC 9110 also notes: if you hide resources to avoid disclosure, `404` is acceptable where
> `403` would be truthful. Pick **one policy per resource class and apply it uniformly** —
> inconsistency is what creates the oracle.

## How it works — the ordered decision

```text
request arrives
  │
  ├─ no/invalid credentials ──────────────▶ 401 + WWW-Authenticate
  │
  ├─ valid credentials
  │    ├─ principal lacks permission AND hiding policy says "deny silently" ─▶ 404
  │    ├─ principal lacks permission, resource may be disclosed ─────────────▶ 403
  │    ├─ resource absent (for this principal/tenant) ───────────────────────▶ 404
  │    ├─ resource existed, now permanently deleted ────────────────────────▶ 410
  │    ├─ path exists, method unsupported ──────────────────────────────────▶ 405 + Allow
  │    └─ otherwise ────────────────────────────────────────────────────────▶ proceed
```

Ordering rule: **authenticate → authorize → locate**. Locating first (a `SELECT` without a
tenant predicate, then an authz check) is how cross-tenant leaks happen; the status code is
just the last mile.

## Worked example — the same project ID, three callers

Acme's `GET /api/v1/projects/pr_842`:

```http
GET /api/v1/projects/pr_842 HTTP/1.1
Authorization: Bearer <expired>
```

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="acme", error="invalid_token",
                  error_description="The access token expired"
Content-Type: application/problem+json

{
  "type": "/problems/unauthenticated",
  "title": "Unauthenticated",
  "status": 401,
  "code": "TOKEN_EXPIRED",
  "detail": "The access token expired at 2026-03-01T09:00:00Z.",
  "requestId": "req_a1"
}
```

```http
GET /api/v1/projects/pr_842 HTTP/1.1
Authorization: Bearer <valid, member-of-another-tenant>
```

→ `404 Not Found` (tenant-hiding policy: never confirm another tenant's IDs exist).

```http
GET /api/v1/projects/pr_842 HTTP/1.1
Authorization: Bearer <valid, member of this project with role viewer>
```

```http
DELETE /api/v1/projects/pr_842 HTTP/1.1
Authorization: Bearer <valid, role viewer>
```

```http
HTTP/1.1 403 Forbidden
Content-Type: application/problem+json

{
  "type": "/problems/forbidden",
  "title": "Forbidden",
  "status": 403,
  "code": "INSUFFICIENT_ROLE",
  "detail": "Deleting a project requires the owner or admin role.",
  "requestId": "req_a3"
}
```

```http
DELETE /api/v1/projects/pr_842 HTTP/1.1
```

→ `405 Method Not Allowed` + `Allow: GET, PATCH` on a read-only subroute, or `403` on the
project resource itself. The distinguishing factor is the **path**, not the verb alone:
`405` when the path is routable but the method is not.

## Key data / numbers

- **`401` requires `WWW-Authenticate`** (RFC 9110 §15.5.2). Bearer challenge example:
  `WWW-Authenticate: Bearer realm="api", error="invalid_token"`.
- **`405` requires `Allow`** (RFC 9110 §15.5.6), e.g. `Allow: GET, HEAD, POST`.
- **`403` has no required header.** `Location` is *not* used here (`3xx` only).
- **Common `401` `error` values** (per RFC 6750 bearer usage): `invalid_request`,
  `invalid_token`, `insufficient_scope`.
- **Existence-hiding decision:** hiding → `404` everywhere; disclosing → `403`. Either is
  valid; **mixing within one resource class is the vulnerability**.
- **`404` for unknown routes** (`GET /api/v1/nope`) and **`404` for unknown resources**
  (`/projects/pr_missing`) share one status by design — route probing stays uninformative.

## Real-world use case — Acme SaaS tenant isolation

Acme's support team kept receiving "403 on project open" tickets from users whose sessions had
expired mid-session: the web app mapped any non-2xx to a generic error, but its retry helper
treated `403` as permanent and stopped — while `401` triggered a silent token refresh. Because
a middleware bug returned `403` for expired tokens, users saw "Access denied" with no way out
until a full logout. The fix: auth middleware returns `401` + `WWW-Authenticate` for every
credential failure; authz middleware is unreachable without a verified principal; the client's
`401` path now refreshes automatically. Related hardening: project reads take `tenant_id` from
the token, and cross-tenant IDs return `404`, eliminating an existence oracle the security
review had flagged.

## Trade-offs

| Approach | Pros | Cons | When to use |
| -------- | ---- | ---- | ----------- |
| Cross-tenant access → `404` | No existence disclosure | Slightly harder to debug for legitimate misroutes | Default for multi-tenant SaaS |
| Cross-tenant access → `403` | Honest; easier support | Confirms resource existence | Internal admin tools, single-tenant |
| `401` for suspended accounts | Triggers re-auth flows | Re-auth won't help; confuses | Prefer `403` with a distinct code (`ACCOUNT_SUSPENDED`) |

## Do / Don't

| ✅ Do | ❌ Don't |
| ----- | -------- |
| Return `401` for every credential failure, with `WWW-Authenticate` | Return `403` for expired tokens |
| Return `403` when a known principal lacks a permission | Return `401` to mask a permission bug |
| Return `404` for resources hidden by policy — consistently | Alternate between `403` and `404` for the same class |
| Return `405` + `Allow` for wrong methods on known paths | Return `404` to "simplify" method handling |

## Common mistakes

- **`401` without `WWW-Authenticate`.** Technically non-compliant; some clients will not
  trigger re-authentication flows.
- **`403` before authentication.** An authz check that runs without a principal produces
  `403` for what are really `401`s — the classic "every request is forbidden" outage.
- **`404`-then-`403` inconsistency.** The same ID returns `404` to members and `403` to
  non-members, confirming existence to exactly the people you meant to hide it from.
- **Using `401` for rate limits.** Some APIs do this to trigger re-auth; it corrupts token
  refresh loops. Rate limits are `429`.

## Checklist

- [ ] Every `401` carries `WWW-Authenticate`.
- [ ] Auth middleware cannot be bypassed onto the authz path.
- [ ] Tenant-scoped lookups filter by tenant in the query, not after the fetch.
- [ ] Each resource class has one documented existence-hiding policy (`403` vs `404`).
- [ ] Every `405` carries `Allow` and is only returned for routable paths.
