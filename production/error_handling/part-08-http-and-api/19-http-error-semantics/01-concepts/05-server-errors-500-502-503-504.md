# Server Errors — 500, 502, 503, 504

> Part VIII · Chapter 19 · Sections 19.13, 19.14, 19.15, 19.16 · _Estimated reading time: 17 min_
> **Prerequisite:** [Status Code Classes and Selection Table](./01-status-code-classes-and-selection-table.md)

## In one sentence

The four server errors answer four different questions — `500` "we hit a bug," `502` "the
upstream sent garbage," `503` "we are (temporarily) unavailable on purpose," `504` "the
upstream never answered" — and choosing the wrong one corrupts client retry behavior and
on-call signal at the same time.

## Why this matters in production

`5xx` responses are the API's loudest signal: load balancers use them for health, circuit
breakers count them to open, SDKs treat them as retry-eligible, and humans treat them as
pages. Precision here has outsized payoff. A bug reported as `503` will be retried by every
client forever (nothing "recovers" from a code defect on a timer) — turning one broken deploy
into amplified load. A dependency outage reported as `500` pages the wrong team: the payments
on-call gets paged for a Stripe incident instead of the integration owner seeing a circuit
breaker trip. **One wrong digit moves the page from the right pager to the wrong one and
multiplies traffic on top of it.**

## Core concept — which 5xx is honest

```text
                ┌──────── 5xx observed by client ────────┐
                │                                         │
     ┌──────────┴──────────┐         ┌────────────────────┴──────────────┐
     │ WE produced it      │         │ The EDGE/GATEWAY produced it       │
     └──────────┬──────────┘         └────────────────────┬──────────────┘
                │                                          │
   ┌────────────┴─────────────┐          ┌────────────────┴───────────────┐
   │ Unhandled condition: bug │          │ Upstream answered, invalidly:  │
   │ broken invariant, our    │          │ 502 Bad Gateway                 │
   │ exception escaped        │          │ Upstream stayed silent: 504     │
   │          → 500           │          │ Gateway knows we're down/       │
   │                          │          │ overloaded: 503                 │
   │ Deliberate/known         │          └────────────────────────────────┘
   │ unavailability: circuit  │
   │ open, maintenance,       │
   │ overload shed: → 503     │
   └──────────────────────────┘
```

- **`500 Internal Server Error`** — an *unexpected condition* on our side: an exception
  escaped, an invariant failed, a bug fired. The client can do nothing but report/retry
  later; it is the "unknown unknown" bucket. Every `500` should correlate to a log/trace
  with a `requestId`.
- **`502 Bad Gateway`** — issued by a **gateway/proxy** that received an *invalid or
  nonsensical response* from an upstream (garbage bytes, illegal status line, connection
  reset mid-response). Your app rarely emits `502`; your edge does. If you are the gateway
  for a dependency, translate upstream breakage to `502` — but see `503` below for the
  "known unavailable" case.
- **`503 Service Unavailable`** — the server is **knowingly not handling requests right
  now**: overload shedding, maintenance mode, an open circuit on a critical dependency, a
  failed readiness check. `503` is the *voluntary* 5xx — and the one that pairs with
  `Retry-After` because recovery is expected.
- **`504 Gateway Timeout`** — the **gateway's** upstream-request deadline expired. Like
  `502`, it is typically edge-issued. An internal timeout of your own code is *not* a `504`:
  it is a `500` (bug/overload in your stack) or contributes to `503` (if you shed load).

> ⚠️ **Hazard.** The most common mislabel: mapping **every** dependency failure to `500`.
> A Stripe outage, a Redis blip, a Postgres failover are *known* conditions with *known*
> recovery — that is `503` (with `Retry-After`), owned by the integration layer, not a `500`
> owned by nobody.

## How it works — selection and translation

Your error registry maps internal codes outward. Excerpt of the mapping Acme uses:

| Internal code | Condition | HTTP | Retryable | `Retry-After` |
| ------------- | --------- | ---- | --------- | ------------- |
| `UNHANDLED_EXCEPTION` | Exception escaped a handler | `500` | No (report it) | — |
| `DB_UNAVAILABLE` | Pool exhausted / failover | `503` | Yes | `5`–`30` s |
| `PAYMENT_PROVIDER_TIMEOUT` | Stripe deadline exceeded | `503` | Yes | `10` s |
| `CACHE_UNAVAILABLE` (degraded path) | Redis down, serving stale | `200`/degraded | — | — |
| `UPSTREAM_INVALID_RESPONSE` | Dependency returned garbage | `502` | Maybe | — |
| `EDGE_UPSTREAM_TIMEOUT` | Gateway deadline | `504` | Yes | — |

Translation rules that keep this honest:

1. **`500` only for genuinely unexpected conditions.** If you can name the class of the
   failure (DB down, provider timeout), it is not a `500` — it has a code, and the code maps
   to `503`/`502`.
2. **`503` when unavailability is detectable and temporary** — breaker open, readiness
   failing, shed load. Attach `Retry-After` when you can estimate recovery (maintenance
   window, breaker half-open delay).
3. **Edge vs app ownership:** if the *gateway* generated the status, your app may never see
   the request. Align gateway timeouts to be *longer* than your app's internal deadline, so
   your app fails first with a precise code instead of a generic `504`.
4. **Never translate `5xx` to `2xx`** "to keep the client happy" — that is §19.17's lie with
   a bigger blast radius.

## Worked example — Checkout with a dead PSP

```http
POST /api/v1/checkout HTTP/1.1
Authorization: Bearer <valid>
Idempotency-Key: idem_31f0

{"planId": "pro_monthly", "paymentMethodId": "pm_99"}
```

```http
HTTP/1.1 503 Service Unavailable
Retry-After: 10
Content-Type: application/problem+json

{
  "type": "/problems/service-unavailable",
  "title": "Service Unavailable",
  "status": 503,
  "code": "PAYMENT_PROVIDER_UNAVAILABLE",
  "detail": "The payment provider is temporarily unreachable. Retry in 10 seconds.",
  "instance": "/api/v1/checkout",
  "requestId": "req_f2",
  "retryAfterSeconds": 10
}
```

What happened inside: the integration layer's circuit breaker was open (Stripe had been
returning `5xx` for 90 seconds), so the request failed fast with `503` **without** calling
Stripe. The client SDK sleeps 10 s and retries with the same `Idempotency-Key` — safe,
because Checkout is idempotent (Chapter 28). Contrast with the bug path: a null invoice line
throws inside the handler → catch-all → `500` with `requestId`, alert fires, no `Retry-After`
(sleeping will not fix a null pointer).

## Key data / numbers

- **RFC 9110 names:** `500` Internal Server Error; `502` Bad Gateway; `503` Service
  Unavailable; `504` Gateway Timeout.
- **`Retry-After` on `503`:** allowed by RFC 9110 and expected by clients; same delta-seconds
  or HTTP-date formats as `429`.
- **All four are "retry-eligible" only with conditions:** `503` yes (after delay, idempotent
  only); `504`/`502` at the edge, yes at the client's discretion; `500` **no** — retrying a
  bug amplifies it.
- **Gateway timeout alignment:** edge timeout (e.g. 60 s) > app request deadline (e.g. 30 s)
  > dependency deadline (e.g. 8 s). Inverted numbers produce `504`s where a precise `503`
  should have been.
- **Error-budget framing:** a sustained `500` rate above ~0.1–0.5% of requests (context
  dependent) typically trips SLO-based alerting; `503` during a known incident is *expected*
  signal, not noise.

## Real-world use case — Acme SaaS AgentRun

`AgentRun` calls an LLM provider with a 25 s internal deadline. The edge gateway timed out at
20 s, so every provider slowdown surfaced to clients as `504 Gateway Timeout` — with no
`requestId`, no provider attribution, and no `Retry-After`. On-call could not tell provider
incidents from Acme bugs. Two changes fixed the signal: (1) internal deadline 15 s < edge 60 s
so the app always fails first, mapping provider timeouts to `503` + `Retry-After: 20` +
provider name in the (safe) detail; (2) breaker on the provider with a half-open probe
delay aligned to `Retry-After`. Within a month, provider incidents were distinguishable from
Acme bugs purely from the status/metadata mix — `503 PAYMENT_PROVIDER_UNAVAILABLE`-style codes
vs `500 UNHANDLED_EXCEPTION` — and client retry behavior stopped amplifying provider load
during outages.

## Trade-offs

| Approach | Pros | Cons | When to use |
| -------- | ---- | ---- | ----------- |
| Dependency failures → `503` + `Retry-After` | Correct retry semantics; routes to integration on-call | Requires per-dependency codes | Default for any external dependency |
| Dependency failures → `500` | Simple catch-all | Mis-pages; clients retry bugs | Never |
| Custom status codes (`4xx` for dep down) | Non-standard "cleverness" | Breaks proxies/SDKs; forbidden by semantics | Never |

## Do / Don't

| ✅ Do | ❌ Don't |
| ----- | -------- |
| Reserve `500` for genuinely unexpected conditions | Map every failure to `500` |
| Return `503` + `Retry-After` for known temporary unavailability | Return `500` during a declared maintenance window |
| Keep edge timeouts longer than app deadlines | Let the edge cut first and erase your error taxonomy |
| Correlate every `500` to a logged stack + `requestId` | Return a bare `500` with no correlation handle |

## Common mistakes

- **`503` without `Retry-After`.** Allowed by the letter of the RFC, useless in practice:
  clients guess, and the herd converges on the same instant.
- **Hiding outages behind `200`.** A circuit-open dependency served as empty success is a
  silent data-integrity landmine (see §19.17).
- **`504` from the app itself.** Your handler is not a gateway. Internal timeouts should
  produce coded `503`s (or `500` if truly unexpected), not `504`.
- **Alerting on all `5xx` equally.** `500` pages immediately; `503` during a known dependency
  incident should route to the incident, not a second page.

## Checklist

- [ ] Every internal error code maps to exactly one 5xx in the registry.
- [ ] Dependency failures produce `503` (+ `Retry-After`), never `500`.
- [ ] Edge/app/dependency timeout budget is ordered and documented.
- [ ] `500`s are alertable and always carry a `requestId` for trace lookup.
- [ ] Maintenance and breaker-open paths emit `503`, not `500`.
