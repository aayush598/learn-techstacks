# Section 01: Futexes and Linux Synchronization

> **TL;DR**: A futex (fast userspace mutex) is a userspace 32-bit word plus two kernel syscalls — `futex_wait` (sleep until the word changes) and `futex_wake` (wake waiters). Lock acquisition stays entirely in userspace (a CAS) when uncontended; the kernel is only involved on contention — making mutexes and condition variables nearly free.

## 1. Why Does This Exist?
A mutex that did a syscall *every* acquire/release would cost ~1µs per op even when uncontended — unacceptable. Futexes exist to move the common case into userspace: a lock is just an atomic operation on a word; the kernel is involved only when a thread actually *contends* (needs to sleep) or must *wake* another. This is why pthread_mutex_lock can be ~20ns uncontended. Futexes are the glue that makes glibc's mutexes, condition variables, semaphores, and rwlocks all fast and correct.

## 2. How Does It Work?
- A futex = a userspace `int` (aligned, shared if needed) + kernel bookkeeping.
- **`futex(WAIT, addr, expected)`**: if `*addr == expected`, sleep the calling thread (enqueue on a kernel wait queue keyed by the address); else return immediately (the word already changed → no sleep needed).
- **`futex(WAKE, addr, n)`**: wake up to n threads waiting on `addr`.
- A mutex fast path: `cmpxchg(word, 0, 1)`; if success → locked, no syscall. If the word shows waiters, the slow path does `futex_wait`/`futex_wake`.
- The word has flags: LOCKED, CONTENDED/Waiters, OWNERDEAD (robust).

## 3. When Is It Used?
- **pthread_mutex, pthread_cond, sem_t, pthread_rwlock** — glibc implements all of these on futexes.
- **Robust mutexes** (process death recovery) and **PI futexes** (priority inheritance for RT mutexes).
- Any userspace library needing an efficient blocking primitive (languages: C++ std::mutex, Rust, Go's futex-based fast path, Java's park/unpark on Linux).

## 4. Why Wasn't Another Approach Chosen?
- **Syscall-every-op (old SYSV semop / scheduler-based locks)**: ~µs per operation, even uncontended. Rejected — futex keeps the common path in userspace.
- **Pure spinlock in userspace**: no sleep → CPU waste under contention. Rejected.
- **Pure kernel mutex for all locks**: syscall cost dominates. Rejected.
- **Hardware-only solutions**: can't sleep. Rejected.
The futex design wins: **userspace atomic for the fast path + kernel wait/wake only on contention** — the right split between speed and blocking.

## 5. Intuition
**A library carrel with a key-card door**: when the carrel is free, you just swipe and walk in — no call to the librarian (no syscall). Only when it's occupied do you need the librarian to put you on the waitlist (futex_wait) and call you when it's free (futex_wake). The whole "is it free?" check happens locally at the door (userspace atomic); the librarian only handles the actual queue.

## 6. Real-World Analogy
**A restaurant's "waiting list" clipboard at the host stand**: checking if a table is free is instant (look at the board — userspace). Only when there are no tables does the host write your name (futex_wait) and call you when a table opens (futex_wake). You don't need to involve the manager (kernel) for every party that walks in — only the ones that must wait.

## 7. Formal Definition
- **Futex**: a userspace `int` at address `addr`, interpreted atomically; kernel associates a wait queue with the address.
- **`futex_wait(addr, val)`**: atomically check `*addr == val`; if so, enqueue the thread and sleep. If `*addr != val`, return immediately.
- **`futex_wake(addr, n)`**: wake up to n threads blocked on `addr`.
- **Mutex word encoding** (glibc): 0 = unlocked; 1 = locked, no waiters; 2+ = locked with waiters (futex waiters → FUTEX_WAKE needed).
- **Operations**: FUTEX_WAIT, FUTEX_WAKE, plus FUTEX_REQUEUE, FUTEX_CMP_REQUEUE, FUTEX_LOCK_PI, FUTEX_WAIT_BITSET, futex2 (32/64-bit, flags).
- **Futex hash table**: kernel hashes `addr` → wait queue (no per-address object allocation until first wait).

## 8. Example
```
word = 0  (unlocked)
Thread A: lock(): cmpxchg(0->1) succeeds. A owns — NO syscall.  [~20ns]
Thread B: lock(): cmpxchg(0->1) fails (word=1). word = 2 (mark waiters).
          futex_wait(word=2) -> kernel parks B.                 [syscall, sleep]
Thread A: unlock(): cmpxchg(1->0) but word had waiters (2) -> futex_wake(1)
          -> B wakes, acquires.                                 [syscall, wake]
```
Uncontended: zero kernel involvement. Contended: one wait + one wake syscall.

## 9. Internal Working
1. User code: atomic compare-exchange on the word. Success → done.
2. Failure path: set the waiters bit (word=2) and call `futex_wait` with the current word value.
3. Kernel: `futex_wait` looks up the wait queue in the futex hash table (per address), adds the task, and sleeps (schedule). Wakeups are generated by `futex_wake` after unlock.
4. Unlock: clear the lock bit; check if waiters flag set → `futex_wake` (n=1 for mutex).
5. **PI futexes**: the waiter tells the kernel the lock's owner; the kernel boosts the owner's priority (inheritance) — used by glibc's PI mutexes.
6. **Robust futexes**: the word encodes OWNERDEAD on owner death; waiters get EOWNERDEAD and can recover.
7. Futex2 (Linux 6.x): supports 32/64-bit words and flags, and no dup address issues.

## 10. Time Complexity
- Uncontended lock/unlock: O(1) atomic (~20-30ns; no syscall).
- Contended: O(1) syscall + scheduler wake (~µs). 
- Futex hash: O(1) lookup; wait queue O(1) enqueue.
- Wake: O(n) for broadcast; O(1) for single.

## 11. Advantages
- Uncontended operations are userspace-only (fast, no syscall).
- Correct sleeping semantics (waiters don't spin).
- Reusable for mutexes, CVs, semaphores, rwlocks.
- PI and robust variants solve inversion and owner-death.
- Works in shared memory → cross-process locks.

## 12. Disadvantages
- Syscall overhead when contended (still ~µs wakeups).
- Word value races require careful handling (FUTEX_WAIT validates the value).
- Not a general "named" object — must share the address.
- Missing futex for a stale address leaks kernel wait queues (hash cleanup handles most).
- Harder to reason about than higher-level primitives (that's why languages wrap them).

## 13. Interview Questions
1. **Q: What is a futex?** A: Fast userspace mutex — a userspace integer + kernel wait/wake syscalls (futex_wait/futex_wake), so uncontended locks never leave userspace.
2. **Q: Why do futexes exist?** A: A syscall per lock op is too slow (~µs); futexes keep the fast path as a userspace atomic and use the kernel only for actually waiting/waking.
3. **Q: What does futex_wait do?** A: Sleeps the calling thread if the word still equals the expected value; returns immediately if it changed (no missed wakeup).
4. **Q: What does futex_wake do?** A: Wakes up to n threads blocked on the futex address.
5. **Q (TRICKY): Why does futex_wait take an expected value?** A: To prevent lost wakeups: if the value already changed, you don't sleep — the state you were waiting for has already happened.
6. **Q: How is a mutex encoded?** A: 0 = unlocked, 1 = locked no waiters, 2+ = locked with waiters (so unlock knows to call futex_wake).
7. **Q: What is a PI futex?** A: A futex with priority inheritance — the kernel boosts the lock holder's priority when a higher-priority thread waits, preventing inversion.
8. **Q: What is a robust futex/mutex?** A: One that detects owner death (OWNERDEAD) so waiters can recover state instead of deadlocking forever.
9. **Q (PRODUCTION): A contended mutex shows high syscall time. What's happening?** A: Threads are futex_wait/futex_wake — sleeping and waking under contention. Reduce contention (sharding, RW locks, lock-free) or accept the scheduler latency.
10. **Q: How do condition variables use futexes?** A: pthread_cond_wait parks on a futex keyed to the CV (with a sequence counter); signal/broadcast futex_wake one/all.
11. **Q: What is futex2?** A: The modernized futex API (Linux 6.3+): 32/64-bit words, flags, and a cleaner interface replacing FUTEX_WAIT/FUTEX_WAKE legacy forms.
12. **Q (TRICKY): Could you implement a mutex with only futex_wait/futex_wake?** A: Yes — word 0/1/2 encoding, cmpxchg fast path, wait/wake on contention: exactly what glibc does. The futex syscalls are the *only* kernel interface needed.

## 14. Follow-Up Questions
1. **Q: What's the difference between FUTEX_WAIT and a spin?** A: FUTEX_WAIT sleeps (parks) — no CPU burn; spinning wastes CPU but avoids syscall latency. Hybrids (optimistic spinning) exist.
2. **Q: How does the kernel find the wait queue for an address?** A: A global hash table keyed by the futex address — no per-futex kernel object is pre-allocated.
3. **Q: What is a "requeue" operation?** A: FUTEX_REQUEUE moves waiters from one futex to another atomically — used by condvar broadcast to avoid a thundering herd.
4. **Q: How does Java's LockSupport relate?** A: park/unpark maps to futex_wait/futex_wake (with a permit token) on Linux — the JVM's blocking primitive.
5. **Q: Why is the fast path so important?** A: In real workloads most locks are uncontended; making that path a userspace atomic is why pthread mutexes cost ~20ns, not ~1µs.

## 15. Coding Example
```c
/* Minimal futex-based mutex (conceptual, glibc-style) */
#include <linux/futex.h>
#include <sys/syscall.h>
#include <stdatomic.h>
#include <unistd.h>
#include <stdint.h>

static int futex(int *uaddr, int op, int val) {
    return syscall(SYS_futex, uaddr, op, val, NULL, NULL, 0);
}

/* 0 = unlocked, 1 = locked, 2 = locked+waiters */
void futex_lock(atomic_int *word) {
    int expected = 0;
    if (atomic_compare_exchange_strong(word, &expected, 1))
        return;                                  /* fast path: no syscall */
    if (atomic_exchange(word, 2) != 0)           /* mark waiters */
        futex((int*)word, FUTEX_WAIT, 2);        /* slow path: sleep */
    /* retry loop omitted for brevity */
}
void futex_unlock(atomic_int *word) {
    if (atomic_fetch_sub(word, 1) != 1)          /* was 2 -> had waiters */
        futex((int*)word, FUTEX_WAKE, 1);        /* wake one */
}
```

```bash
strace -e trace=futex ./some_threaded_program 2>&1 | head
```

## 18. Cheat Sheet
- Futex = userspace word + FUTEX_WAIT/FUTEX_WAKE.
- FUTEX_WAIT: sleep if word == expected (else return).
- FUTEX_WAKE: wake n waiters.
- Fast path: cmpxchg 0→1, no syscall (~20ns).
- Word encoding: 0/1/2 (unlocked/locked/locked+waiters).
- Contended: ~µs (syscall + scheduler).
- PI futex: priority inheritance (inversion fix).
- Robust: OWNERDEAD recovery.
- CVs, semaphores, rwlocks all built on futexes.
- futex2: 32/64-bit, flags (Linux 6.3+).

## 21. Revision
A futex is a userspace integer plus kernel FUTEX_WAIT/FUTEX_WAKE: uncontended lock ops are a userspace CAS (no syscall, ~20ns); contention parks threads in a kernel wait queue keyed by address. Mutex word encoding (0/1/2) tells unlock whether to wake. PI futexes add priority inheritance; robust futexes recover from owner death. Everything — pthread mutexes, CVs, semaphores, rwlocks, JVM/Go/Rust blocking — builds on futexes. It's the reason modern locks are cheap when uncontended and still correct when contended.
