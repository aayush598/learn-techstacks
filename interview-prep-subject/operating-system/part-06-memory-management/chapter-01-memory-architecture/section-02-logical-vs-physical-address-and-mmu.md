# Logical vs Physical Address and the MMU

> **TL;DR**: The CPU generates **logical (virtual) addresses**; the **MMU (Memory Management Unit)** translates each one into a **physical address** on the memory bus using base/limit or page tables, enforcing protection on every single memory access.

## 1. Why Does This Exist?
A CPU that shipped physical addresses straight to RAM would force the OS to load every process at a fixed location and would give every process access to all of memory. The MMU exists to insert a *hardware check-and-translate step* into the address path: it turns "what the program thinks it's addressing" (logical) into "what RAM actually is" (physical) while simultaneously rejecting any access outside the process's authorized region. This is the hardware anchor that makes the OS's memory abstractions (protection, paging, virtual memory, ASLR) possible at instruction speed. Without an MMU, all of Part 06 and Part 07 would be software-only and far too slow to be usable.

## 2. How Does It Work?
For each memory access generated by the CPU:
1. The CPU emits a **logical address** (from the program counter fetch, or a data reference).
2. The MMU applies the translation rule for that process:
   - **Simple mode**: add `base` register, reject if ≥ `base+limit`.
   - **Paged mode**: split the address into `page number | offset`, index the page table (via the `CR3`/`PTBR` register), combine the resulting **frame number** with the offset → physical address; fault if the entry is invalid or the page not present.
3. The **physical address** is placed on the bus and served from RAM/cache.

The user process *never* sees physical addresses; the OS maintains the translation data (page tables) that the MMU consumes.

## 3. When Is It Used?
- **Every user-mode instruction** on Linux/Windows/macOS/BSD: every `LOAD`, `STORE`, and instruction fetch goes through the MMU.
- **Kernel too**: modern kernels are also paged (e.g., `CONFIG_RANDOMIZE_BASE`, page tables for kernel text), though they may use large pages and keep direct-map regions.
- **Virtual machines**: the hypervisor uses a second-level MMU (EPT/NPT on Intel/AMD) to translate guest-physical → host-physical — the MMU concept applied recursively.
- **I/O**: DMA does *physical* addressing (the device bypasses the MMU), which is why drivers use `dma_alloc_coherent` / bounce buffers for pages the device can address.

## 4. Why Wasn't Another Approach Chosen?
- **Pure software translation (base-register only, done in the scheduler)**: works (classic UNIX), but only *between* runs — a process that's running cannot be moved, and every access still hits the real address. Rejected: no per-access protection, no paging.
- **Emulation in software per access**: a "virtual machine monitor" that checks every load in software. Rejected: orders of magnitude too slow.
- **Segmented MMU only (Intel 8086/x86-16)**: provides base+limit segments but with a tiny 64 KB granularity and a 20-bit address space — awkward and fragmented (see Part 06 Ch. 04).
- **Single global page table (no per-process)**: no isolation — rejected immediately.
- **Memory-protection key (MPK)**: a newer, cheaper hardware scheme (Intel PKU) that protects *regions* with keys rather than translating per page; used as a *supplement* for fast domain switching, not a replacement for translation.

## 5. Intuition
The MMU is a bouncer with a guest list. Every process carries its own "guest list" (page table / base+limit) that says exactly which rooms it may enter and where those rooms actually are. Every time the process knocks (memory access), the bouncer consults the list, walks them to the real room, and throws them out (fault) if the room isn't theirs. The process never sees the real floor plan — only the bouncer does.

## 6. Real-World Analogy
An airline boarding pass shows **Gate A5** (logical address). The airport's display system (MMU) maps "Gate A5" to the *physical* location "Terminal 2, Pier C, bay 7" and refuses boarding if your pass says a gate that doesn't exist for your flight (out-of-range → fault). The passenger navigates by the label; the airport maps it to the building.

## 7. Formal Definition
A **logical (virtual) address** is an address generated by the CPU during instruction execution; a **physical address** is the address actually presented to the memory unit. The set of logical addresses is the *logical address space*; the set of physical addresses is the *physical address space*. The **MMU** is the hardware component (usually inside the CPU, driven by privileged control registers) that maps logical to physical addresses and raises exceptions on invalid accesses; its runtime mapping state is maintained by the OS in structures such as page tables, referenced via the page-table base register.

## 8. Example
32-bit system, page size 4 KB, process's page table (frame per entry):

| Page # (logical bits 31..12) | Frame # (physical) |
|---|---|
| 0 | 7 |
| 1 | 12 |
| 2 | 3 |

Instruction `LOAD R1, 0x21A0` → page = 0x21A0 >> 12 = 0x2, offset = 0x1A0.
MMU: page 2 → frame 3 → physical = 3×4096 + 0x1A0 = 0x31A0.
If instead the program accessed page 5 (not in the table): MMU raises a page fault → kernel decides to map a frame or kill the process (SIGSEGV).
Note: logical 0x21A0 = 8.6 KB; physical 0x31A0 = 12.7 KB — the same offset, different base, exactly like base/limit with 4 KB granularity instead of one big block.

## 9. Internal Working
1. CPU fetches instruction at logical address PC (e.g., 0x1000). PC is *logical*; the MMU translates before the fetch hits L1 cache (VIPT/physically-indexed caches are tagged with physical addresses).
2. On an **x86-64** machine, the MMU reads `CR3` to get the PML4 base of the current process's page table.
3. It walks the **4-level table**: bits 47:39 → PML4 entry, 38:30 → PDPE, 29:21 → PDE, 20:12 → PTE. Each entry is 8 bytes; bits 63 (NX), 0 (present), 1 (rw), 2 (user), 5 (accessed), 6 (dirty) are checked.
4. If a level's entry has `present=0` or violates permissions, the MMU raises a **#PF (page-fault) exception**; the kernel's fault handler (`do_page_fault` / `handle_page_fault`) runs.
5. On success: physical address = PTE's PFN<<12 | offset. The result is cached in the **TLB** so the next access skips the walk.
6. For DMA and I/O, the device uses *physical* addresses; the OS either maps buffers with `dma_map_single` or uses an IOMMU (a second MMU for devices) to let devices also use virtual addresses.

## 10. Time Complexity
- Base/limit translation: O(1) (add + compare).
- Paged translation, TLB hit: O(1) in hardware (parallel CAM lookup).
- Paged translation, TLB miss: O(L) table lookups, L = 4 on x86-64 (each ~1–2 cycles), then the TLB entry is cached; amortized cost per access ≈ hit-rate × 1 + miss-rate × L.
- Page-fault handling: O(page-table setup) + O(1) frame allocation; the *I/O* to load a page from disk dominates (~ms) vs ~1 ns for a TLB hit.
- Context switch flushing TLB: O(1) flush (or O(#entries) for targeted invalidation via `invlpg`).

## 11. Advantages
- **Per-access protection** enforced in hardware, impossible to bypass from user mode.
- **Fine-grained mapping**: pages can be shared (same frame in many tables), marked read-only/exec, demand-loaded.
- **Relocation is O(1)** per process (change tables, not code).
- Enables **virtual memory**: sparse 2⁶⁴ virtual space mapped to far less RAM (Part 07).
- **Isolation between processes and user/kernel**.

## 12. Disadvantages
- **Translation latency** per access — mitigated by TLB + hardware page-walk caches.
- **TLB is finite** (a few hundred to a few thousand entries); large working sets thrash it.
- Page-table **memory overhead** (mitigated by multilevel + large pages).
- Hardware **complexity** and silicon area; must be disabled on some real-time/safety systems where deterministic latency is required.
- Page faults are expensive (trap into kernel, possible I/O) — unpredictable if frequent.

## 13. Interview Questions
1. **Q: What's the difference between a logical and a physical address?** A: Logical is what the CPU/program generates within its virtual space; physical is the address that reaches the memory bus. The MMU translates one to the other per access.
2. **Q: Where does the MMU live and how does the CPU invoke it?** A: The MMU is part of the CPU memory subsystem; the CPU feeds it every address and the control registers (e.g., CR3) define the active mapping for the current process.
3. **Q: Who updates the MMU's page table pointer? (Tricky)** A: Only the OS (privileged code), on context switch — the kernel loads CR3 with the new process's PML4 pointer; user code can never modify translation state.
4. **Q: What happens during a page fault?** A: The MMU raises #PF; CPU traps to the kernel; `do_page_fault` inspects the faulting address (CR2 on x86) and the error code, decides whether it's a valid access (e.g., demand paging → allocate frame, read page from disk) or a violation → SIGSEGV to the process.
5. **Q: Why do caches use physical addresses but the CPU generates logical ones? (Scenario)** A: Two processes could map the same logical address to different frames; if caches were tagged logically, stale entries would leak data between processes. So L2/L3 are physically indexed/tagged; VIPT L1 uses the offset bits (identical in logical & physical for aligned pages) to stay fast.
6. **Q: What is the relationship between page size and the offset field?** A: For a 4 KB page, the low 12 bits are the offset (index within the page), unchanged by translation; the high bits select the frame. The sum of offset bits + PFN bits must equal the physical address width.
7. **Q: How does a hypervisor handle guest translation? (Production)** A: With EPT (Intel) / NPT (AMD), the guest OS's page tables translate guest-virtual→guest-physical, and the *hardware* MMU does a second level guest-physical→host-physical, so VMs need no hypervisor trapping for every access.
8. **Q: Can user processes bypass the MMU to read arbitrary RAM? (Tricky)** A: Not through normal loads/stores. But they can arrange *DMA* through a driver, or use `/dev/mem`, `process_vm_readv`, or a kernel exploit — which is why kernels forbid mapping of physical memory to user space by default (`CONFIG_STRICT_DEVMEM`).
9. **Q: Why is the TLB needed if translation is only O(1)?** A: A 4-level walk is 4+ dependent memory loads per access — too slow (4×L2 latency). The TLB caches page→frame so a hot mapping costs ~1 cycle, not ~50.
10. **Q: When would you choose huge pages (2 MB / 1 GB)? (Scenario)** A: For large working sets (databases, Java heaps, VMs), to reduce TLB misses and page-table depth; Linux supports `THP` (transparent huge pages) and `hugetlbfs` for this. Trade-off: coarser granularity, less flexible sharing/partial-fault handling.
11. **Q: What does the NX bit do?** A: No-eXecute — marks a page as non-executable; the MMU rejects instruction fetches from it. It's the hardware basis for W^X (write XOR execute) hardening, killing classic buffer-overflow shellcode injection.
12. **Q: How does the kernel get its own memory if the MMU is per-process? (Tricky)** A: On Linux x86-64 the kernel occupies the top half of *every* process's 4-level table (a common global mapping), so user processes carry kernel mappings that are privileged (U/S bit clear) — user access to them faults.
13. **Q: What is a "dirty" bit and why does the MMU maintain it?** A: Hardware sets it when a page is written, so the OS knows which pages must be written back to disk on eviction — avoiding needless writes of clean pages. The OS can't track every write in software without huge overhead.
14. **Q: What is the IOMMU? (Production)** A: An MMU for devices: it translates *device* DMA addresses, letting drivers use virtual addresses and preventing buggy/malicious devices from reading arbitrary RAM. Required for safe device assignment (VFIO, DPDK).

## 14. Follow-Up Questions
1. **Q: How does a context switch flush the TLB?** A: The kernel writes CR3 with the new page table base — on x86 this implicitly flushes the entire TLB (plus `invlpg`/PCID for targeted invalidation in modern CPUs).
2. **Q: What are PCID/ASIDs for?** A: Process-context IDs tag TLB entries with the owning process, so switching processes doesn't require flushing everything — big performance win for context-switch-heavy workloads.
3. **Q: What's a "page-table walk cache" (PWT)/paging-structure cache?** A: Caches the intermediate levels of the 4-level walk so a cold TLB miss costs ~1–2 accesses instead of 4.
4. **Q: Why do some CPUs offer 5-level paging?** A: x86-64 with 57-bit virtual addresses (LA57) adds a 5th level to support >128 TB address spaces and larger databases; Linux supports it with `CONFIG_X86_5LEVEL`.
5. **Q: What is W^X and how is it enforced?** A: Policy that no page is simultaneously writable and executable; enforced by the MMU using the R/W + NX bits, defeating JIT-shellcode and ROP prep.

## 15. Coding Example
```c
// Simulate a single-level page-table translation on a 32-bit system, 4K pages
#include <stdio.h>
#include <stdint.h>

#define PAGE_SHIFT 12
#define PAGE_SIZE  (1u << PAGE_SHIFT)   // 4096

// 20-bit frame numbers; entry 0xFFFF == invalid (not present)
uint16_t page_table[1 << 20];

int translate(uint32_t logical, uint32_t *physical) {
    uint32_t page  = logical >> PAGE_SHIFT;   // top 20 bits
    uint32_t off   = logical & (PAGE_SIZE - 1);// low 12 bits
    uint16_t frame = page_table[page];
    if (frame == 0xFFFF) return -1;            // page fault / SIGSEGV
    *physical = ((uint32_t)frame << PAGE_SHIFT) | off;
    return 0;
}

int main(void) {
    page_table[2] = 3;                        // page 2 -> frame 3
    page_table[1] = 0xFFFF;                   // page 1 invalid
    uint32_t phys;
    printf("0x21A0 -> ");
    if (translate(0x21A0, &phys) == 0) printf("0x%x\n", phys); else printf("FAULT\n");
    if (translate(0x1234, &phys) != 0) printf("access to page 1: FAULT\n");
    return 0;
}
```

## 16. Industry Usage
- **Linux**: `arch/x86/mm/fault.c` (`do_page_fault`), `mm/memory.c`, huge pages (`mm/hugetlb.c`), THP (`mm/huge_memory.c`); `arch/x86/include/asm/pgtable_types.h` defines PTE bits (present, rw, user, accessed, dirty, NX).
- **Intel/AMD**: PML4/paging-structure hierarchy, PCID/ASID, EPT/NPT, MPK (protection keys).
- **ARM64**: stage-1 (VA→PA) + stage-2 (IPA→PA for VMs), 4 KB/16 KB/64 KB pages, TLB by ASID.
- **VMs**: KVM uses EPT to run guest page tables natively; VFIO/DPDK rely on IOMMU for safe passthrough.
- **Browsers**: Chrome/V8 use W^X + MPK to isolate JIT code from data; Android uses `mprotect` region flipping.

## 18. Cheat Sheet
- CPU emits **logical**; MMU emits **physical**; bus sees physical.
- MMU state = base/limit or page-table base register (CR3); OS-only writes.
- 4K page ⇒ offset = low 12 bits; frame = high bits; PTE holds PFN.
- TLB caches translations; miss = 4-level walk; hit = ~1 cycle.
- #PF → kernel `do_page_fault` → demand page or SIGSEGV.
- NX + W^X defeat shellcode; accessed/dirty bits drive paging decisions.
- x86-64: 4-level default, 5-level with LA57; huge pages reduce walks.
- IOMMU = MMU for DMA devices.

## 20. Flashcards
- **Q: Logical vs physical address?** → **A:** Logical = CPU-generated virtual address; physical = address on the memory bus after MMU translation.
- **Q: What does the MMU do?** → **A:** Translates logical→physical per access and enforces protection (base/limit or page tables), faulting on violations.
- **Q: What is a TLB?** → **A:** Cache of recent logical→physical translations; avoids the 4-level page walk on every access.
- **Q: What raises a page fault?** → **A:** A PTE with present=0 (or permission violation); the kernel decides to load the page or SIGSEGV.
- **Q: What does the NX bit enforce?** → **A:** Pages can't be executed, enabling W^X against shellcode injection.
- **Q: How is translation made fast?** → **A:** TLB hit (~1 cycle); hardware page-walk caches; huge pages for large working sets.

## 21. Revision
The CPU only ever deals in logical addresses; the MMU — controlled exclusively by the kernel through registers like CR3 and the active page table — translates each access into a physical address and enforces protection per page. A 4 KB page gives 12 offset bits + a 20-bit PFN (32-bit) or a 4-level walk (x86-64); the TLB caches mappings so hot accesses cost ~1 cycle. Faults (present=0 / permission) raise #PF, which the kernel resolves by demand-loading or killing the process with SIGSEGV. The NX bit enforces W^X; IOMMUs extend the same idea to DMA devices. This per-access hardware translation is the engine behind every memory-management feature in this part and virtual memory in Part 07.
