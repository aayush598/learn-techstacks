# Network System Design Round — 100 Interview Q&A

## Q1: What are the core principles behind designing a globally distributed CDN?

**A:** A globally distributed CDN is built on three pillars: proximity-based content delivery, intelligent request routing, and origin offloading. The fundamental idea is to push cached content as close to end users as possible, minimizing the round-trip distance packets must travel. This is achieved by deploying edge nodes across thousands of points of presence (PoPs) in major metropolitan areas and internet exchange points worldwide. The CDN intercepts DNS queries and directs users to the nearest edge using anycast IP addresses or geographic DNS resolution, ensuring the first network hop is always short.

The second principle is cache hierarchy and origin shielding. Most CDNs employ a multi-tier architecture: edge caches sit in front of regional mid-tier caches, which in turn pull from the origin. This shields the origin from stampede traffic, as a cache miss at the edge may be served by the mid-tier without reaching the origin. Cache invalidation strategies like TTL-based expiration, purge APIs, and versioned URLs control freshness. Write-through and write-behind caching patterns ensure consistency for dynamically generated content.

The third principle is resilience and fault isolation. A well-designed CDN must handle partial failures gracefully. If one edge cluster goes down, traffic shifts to the next-closest cluster via health-checked DNS or BGP route withdrawal. The CDN must also handle origin failures by serving stale content when configured, implementing graceful degradation. Capacity planning at each tier ensures that no single location becomes a bottleneck during traffic spikes such as live events or product launches.

## Q2: How does DNS-based load balancing work at CDN scale?

**A:** DNS-based load balancing at CDN scale uses a combination of authoritative DNS resolution and intelligent response selection. When a client resolves a domain, the CDN's authoritative name server returns one or more IP addresses selected based on factors like the client's source IP geolocation, current server health, real-time load metrics, and network proximity. Anycast is commonly layered on top, where the same IP prefix is announced from multiple PoPs via BGP, and the internet's routing fabric naturally directs each client to the nearest advertising PoP.

The authoritative DNS server must make sub-millisecond decisions, which means it operates in-memory with pre-computed routing tables rather than performing real-time lookups. Health checks run continuously against edge servers, and unhealthy nodes are removed from DNS responses within seconds. Weighted round-robin, least-connections heuristics, and latency-based routing are common algorithms. Some CDNs also implement GeoDNS, which maps specific IP ranges or ASN groups to preferred edge locations, bypassing pure geographic distance when network topology makes a geographically closer server actually slower.

The key limitation of DNS-based load balancing is TTL control. Short TTLs allow faster failover but increase DNS query volume, while long TTLs reduce DNS load but delay failover. Most CDNs mitigate this by using short TTLs (60 seconds or less) at the edge while relying on anycast for coarse-grained routing. Client-side DNS resolvers, ISP resolvers, and intermediate caches can all override TTL settings, so CDNs combine DNS-based routing with HTTP-level redirection and connection-level failover as defense in depth.

## Q3: What is the difference between push and pull CDN caching models?

**A:** In a pull CDN (also called origin-pull), the edge cache does not have content pre-loaded. When a client requests content, the edge checks its local cache; on a miss, it fetches the content from the origin (or a parent cache) and stores it for subsequent requests. This model is self-populating and simple to operate, as content flows to the edge on demand. The tradeoff is that the first request for any asset incurs the full latency of fetching from origin, which can be problematic for large files or during cold starts.

In a push CDN (also called origin-push), content is proactively distributed from the origin to edge caches before clients request it. The origin or a control plane pushes assets to edge nodes based on predicted demand, publication events, or explicit API calls. This eliminates cold-start latency at the edge and gives operators fine-grained control over what is cached where. The downside is increased operational complexity, higher storage costs at the edge, and the risk of pushing content that is never requested, wasting bandwidth.

Most production CDNs use a hybrid approach. Static assets with predictable access patterns (JavaScript bundles, images, video segments) are pre-pushed to edges to guarantee low-latency delivery. Long-tail or user-generated content uses pull caching to avoid excessive storage. Some CDNs implement predictive pre-fetching, using machine learning models trained on access patterns to push content to edges before demand spikes, combining the latency benefits of push with the efficiency of pull.

## Q4: How would you design a URL shortener service with global reach?

**A:** A globally distributed URL shortener requires careful attention to uniqueness, collision avoidance, and low-latency redirect performance. The core design involves a base62 encoding of a monotonically increasing counter or a snowflake-style distributed ID. A centralized counter with a database sequence is simple but creates a single point of failure and bottleneck at global scale. A better approach is to assign each datacenter a unique range of IDs, allowing local generation without coordination. This works with a 64-bit ID split into a datacenter identifier, timestamp, and sequence number.

The storage layer uses a globally distributed key-value store (like DynamoDB, Cassandra, or a custom solution) with the short code as the primary key and the destination URL as the value. Writes are infrequent compared to reads, so the system is read-heavy and benefits from aggressive caching. Each datacenter caches hot URLs in a local Redis or Memcached cluster. For a URL shortener, the read-to-write ratio is typically 100:1 or higher, making caching extremely effective.

The redirect path must be optimized for sub-10ms latency at the edge. The service itself can be deployed as a lightweight function at CDN edge locations, eliminating the round-trip to an origin. When a user hits a short URL, the CDN edge looks up the destination in its local cache or the backing store, and issues an HTTP 301 or 302 redirect. Rate limiting and abuse detection (spam, phishing) are integrated at the edge to prevent malicious URL creation. Analytics collection happens asynchronously via write-behind queues to avoid adding latency to the redirect path.

## Q5: What is anycast routing and how does it help with global load balancing?

**A:** Anycast is a network addressing and routing methodology where the same IP address is announced from multiple geographic locations simultaneously. BGP (Border Gateway Protocol) advertisements propagate these prefixes across the internet, and each router along the path selects the nearest route based on AS-path length, local preference, and other BGP attributes. The result is that clients naturally connect to the topologically closest server without any client-side logic or DNS manipulation.

Anycast provides inherent load balancing because traffic distribution follows the natural density and topology of the internet. If one anycast location becomes overloaded, operators can withdraw or de-prioritize its BGP announcement, shifting traffic to nearby alternatives. It also provides instant failover: when a datacenter goes offline, BGP reconverges within seconds to minutes, routing traffic to the next-closest site. This makes anycast excellent for DNS infrastructure (root servers, TLD servers) and CDN edge deployments.

However, anycast has limitations. BGP routing is not perfectly deterministic; different clients in the same city may route to different anycast sites depending on their ISP's peering arrangements. This can lead to uneven load distribution. Anycast also struggles with connection-oriented protocols like TCP, because if the route changes mid-connection (due to BGP reconvergence), the connection may break. CDNs solve this by using anycast for initial connection establishment and then relying on HTTP-level redirects or sticky sessions. Additionally, anycast provides coarse-grained load balancing (per-PoP) rather than per-server, so a separate layer of load balancing within each PoP is still needed.

## Q6: How does HTTP caching at CDN edges work?

**A:** HTTP caching at CDN edges operates by interpreting and enforcing cache-control headers from the origin while applying local heuristics. The CDN edge cache stores responses keyed by a combination of URL, query parameters, and relevant request headers (like Accept-Encoding). When a request arrives, the cache performs a lookup and applies validation logic based on Cache-Control, Expires, ETag, and Last-Modified headers. A cache hit returns the stored response directly; a cache miss triggers a fetch from the origin or parent cache.

Cache-Control directives provide the primary freshness policy. `max-age` specifies how long an asset is considered fresh; `s-maxage` overrides this specifically for shared caches like CDNs; `no-cache` requires revalidation on every request; `no-store` prevents caching entirely. The CDN parses these directives and enforces them, but may also apply its own override policies. For example, even if the origin sets `s-maxage=300`, the CDN may cap maximum cache duration based on internal policies for certain content types.

Validation caching is critical for reducing bandwidth while maintaining correctness. When an asset expires, the edge sends a conditional request to the origin with `If-None-Match` (using the ETag) or `If-Modified-Since` (using the Last-Modified timestamp). If the asset hasn't changed, the origin returns 304 Not Modified, saving the full transfer. The CDN renews its cached copy's freshness period. Advanced CDNs also support surrogate keys and purge APIs, allowing applications to tag cached content and invalidate specific subsets on demand, which is essential for dynamic content scenarios like news sites or e-commerce product pages.

## Q7: What is cache invalidation and what strategies exist?

**A:** Cache invalidation is the process of ensuring that stale or incorrect content is removed from caches so that subsequent requests receive updated content from the origin. It is notoriously difficult because distributed caches span many nodes, network partitions can delay invalidation propagation, and application code must reason about consistency boundaries. The fundamental challenge is that in a distributed system, you cannot guarantee all caches are invalidated simultaneously; some requests may still hit stale copies during the propagation window.

Time-based expiration (TTL) is the simplest strategy. Each cached asset has a maximum lifetime, after which it is considered stale and must be revalidated or re-fetched. This is passive—it doesn't actively remove content but ensures staleness is bounded. Versioned URLs or cache-busting query strings (e.g., `style.css?v=2`) are widely used for static assets. When deploying a new version, the old URL simply expires naturally, and new requests hit the new URL which is uncached. This avoids explicit invalidation entirely but doesn't work well for dynamically generated content.

Active invalidation strategies include purge APIs (sending explicit invalidation commands to all edge nodes), surrogate-key tagging (tagging cached responses with logical keys and purging by key), and broadcast invalidation via message queues. Purge propagation latency varies: some CDNs guarantee sub-second global propagation, others may take several seconds. The consistency model after a purge is eventual—there is always a window where some edges still serve stale content. Sophisticated implementations use a negative-cache or "purge token" approach where a purge request generates a version stamp, and caches check this stamp before serving content, effectively making stale content serve as a cache miss after the stamp advances.

## Q8: How do you handle cache stampede and cache avalanche problems?

**A:** Cache stampede (also called thundering herd) occurs when a popular cached item expires or is evicted, and many concurrent requests simultaneously attempt to re-fetch it from the origin, overwhelming the backend. Cache avalanche is a related but distinct problem where many cached items expire at the same time (often because they were loaded with identical TTLs), causing a sudden massive spike in origin traffic. Both problems can take down origin servers that are sized for normal miss rates, not 100% miss rates.

To prevent cache stampede, implementations use locking mechanisms such as distributed locks (e.g., Redis SETNX) so that only one request fetches from the origin while others wait or receive stale content. Probabilistic early expiration (XFetch) is another technique where each request has a probability of refreshing the cache before actual expiration, spreading the refresh load over time. Stale-while-revalidate caching serves stale content to concurrent requests while one request asynchronously refreshes the cache, providing seamless user experience during refresh windows.

For cache avalanche, the primary defense is TTL jitter. Instead of setting a uniform `max-age=300` for all assets, add a random offset (e.g., `max-age=300 ± random(0, 60)`) so that items expire at different times. Background refresh threads can pre-warm cache entries before they expire, ensuring continuous freshness. Circuit breakers on the origin protect against overwhelming traffic; when origin error rates exceed thresholds, the CDN can serve stale content and return a degraded response rather than hammering a struggling backend.

## Q9: What is the difference between a reverse proxy and a forward proxy?

**A:** A forward proxy sits between clients and the internet, acting on behalf of clients. It is configured in the client's browser or operating system, and all outbound requests pass through it. Forward proxies are used for content filtering, anonymity, access control, and bypassing geographic restrictions. The origin server sees the proxy's IP address, not the client's. Corporate networks commonly deploy forward proxies to enforce acceptable use policies and cache outbound content to reduce bandwidth.

A reverse proxy sits in front of origin servers, acting on behalf of the servers. Clients are unaware of the reverse proxy; they connect to what they believe is the origin, but the reverse proxy intercepts all requests and forwards them to appropriate backend servers. Reverse proxies provide load balancing, SSL termination, caching, compression, rate limiting, and security (WAF functionality). CDNs are essentially massive reverse proxy networks. NGINX, HAProxy, and Envoy are common reverse proxy implementations.

The key architectural distinction is the direction of initiation and trust. A forward proxy is trusted by clients and untrusted by servers; a reverse proxy is trusted by servers and untrusted by clients. In a CDN context, the edge server acts as a reverse proxy: it terminates the client connection, applies policies, and establishes a new connection to the origin. This separation of concerns allows operators to scale, secure, and optimize the backend independently of the client-facing infrastructure.

## Q10: How does geographic routing work for globally distributed applications?

**A:** Geographic routing in the context of globally distributed applications uses a combination of DNS resolution, BGP anycast, and application-layer logic to direct clients to appropriate regional backends. The first layer is typically DNS-based: an authoritative DNS server examines the client's source IP (often from the EDNS0 client subnet extension for better accuracy behind resolvers) and returns IP addresses of the nearest regional deployment. This provides coarse-grained routing at the DNS level.

BGP-based geographic routing adds another layer by leveraging the internet's routing infrastructure. Anycast prefixes are announced from specific locations, and BGP's path selection naturally routes clients to topologically nearby sites. However, BGP's notion of "nearby" is based on AS-path length and peering relationships, not strict geographic distance. A server in New York might be topologically closer to a European client than one in California due to transatlantic cable paths. This is why CDNs combine BGP anycast with application-layer intelligence.

Application-layer routing provides the finest granularity. Once a client reaches an edge, the application can measure actual latency to various backends and route subsequent requests accordingly. Client-side latency probes, synthetic monitoring, and real-user measurement (RUM) data feed into routing decisions. Global server load balancing (GSLB) systems continuously evaluate backend health and latency, adjusting DNS responses or directing clients via HTTP redirects. This multi-layered approach ensures that routing decisions balance proximity, capacity, and health across the entire global infrastructure.

## Q11: What is BGP and how does it relate to CDN routing?

**A:** Border Gateway Protocol (BGP) is the routing protocol that interconnects autonomous systems (ASes) on the internet. Each AS (typically an ISP, large enterprise, or cloud provider) uses BGP to advertise its IP prefixes to neighboring ASes, and routers propagate these advertisements to build a global routing table. BGP makes path-selection decisions based on attributes like AS-path length, local preference, MED (Multi-Exit Discriminator), and community tags, rather than purely on geographic proximity.

For CDNs, BGP is the foundational mechanism for traffic routing. CDNs announce their IP prefixes from multiple datacenter locations using anycast, allowing the global BGP mesh to direct clients to the nearest point of presence. When a CDN deploys a new edge or takes one offline, it withdraws or advertises the corresponding BGP prefix, and the internet reconverges within seconds to minutes. CDNs also use BGP communities and prepending to fine-tune traffic distribution, steering more traffic toward specific locations or away from congested paths.

BGP also enables CDN interconnection. CDNs peer at internet exchange points (IXPs) and establish private peering arrangements with major ISPs to minimize the number of AS-hops between clients and edge servers. Some CDNs run their own backbone networks (like Google's B4 or Cloudflare's backbone) connecting their PoPs, bypassing the public internet for inter-PoP traffic. This private backbone provides predictable latency, avoids congestion on public links, and enables the CDN to carry cache-fill traffic (from origin to edge) over optimized paths.

## Q12: How would you design a DNS service for a global application?

**A:** Designing a global DNS service requires building an authoritative DNS platform that handles millions of queries per second with sub-50ms resolution times and high availability. The architecture starts with anycast: the same IP addresses are announced from multiple datacenters worldwide. Client queries reach the nearest datacenter via BGP routing, providing automatic geographic distribution without any application logic.

Within each datacenter, the DNS service uses an in-memory database optimized for high-throughput lookups. DNS records are stored in a replicated data store with eventual consistency. Zone transfers (AXFR/IXFR) or API-driven updates propagate record changes across datacenters. Read replicas at each edge serve queries locally, while writes are coordinated through a consensus protocol (like Raft) to prevent split-brain scenarios where different datacenters serve conflicting records for the same zone.

The service must handle DDoS attacks, which frequently target DNS infrastructure. Rate limiting, response-rate limiting (RRL), and DNSSEC for authentication are essential. Health checking and automatic failover ensure that if one datacenter becomes unreachable, BGP withdrawals redirect traffic to surviving sites. For internal DNS (service discovery), the system integrates with health check systems and can dynamically update records based on service availability, enabling automatic failover at the application layer.

## Q13: What is the role of TLS termination at CDN edges?

**A:** TLS termination at CDN edges is the process of decrypting client TLS connections at the edge server and establishing separate encrypted (or unencrypted) connections to origin servers. This serves multiple purposes. First, it offloads the computationally expensive TLS handshake and encryption/decryption from origin servers, allowing them to focus on application logic. Modern CDN edges use hardware acceleration (AES-NI, QAT cards) to handle millions of TLS handshakes per second efficiently.

Second, TLS termination at the edge enables centralized certificate management. Instead of deploying TLS certificates to thousands of origin servers, certificates are managed at CDN edge locations. The CDN handles certificate renewal, OCSP stapling, and protocol negotiation. This also enables TLS 1.3 and modern cipher suites to be negotiated at the edge even if origins support older protocols, protecting end users from downgrade attacks.

Third, edge TLS termination provides visibility into encrypted traffic for security purposes. The CDN can inspect decrypted requests for WAF rules, bot detection, and DDoS mitigation before re-encrypting and forwarding to the origin. The security model requires careful trust: the CDN must be trusted with plaintext traffic, which is why major CDNs invest heavily in security certifications and offer client-side E2E encryption options. The edge-to-origin connection uses a separate TLS session, often over a private network or VPN, providing defense-in-depth if the CDN's internal network is compromised.

## Q14: How does content compression work in a CDN?

**A:** Content compression in a CDN reduces the size of HTTP responses transferred between the edge and clients, directly reducing latency and bandwidth costs. The most common approach is origin-driven compression, where the origin server compresses responses (typically using gzip or Brotli) and the CDN caches and serves the pre-compressed content. This is simple but means the CDN cannot adapt compression to client capabilities—if the origin doesn't support Brotli but the client does, the CDN serves the uncompressed or gzip-only version.

Edge compression (also called dynamic compression) is more flexible. The CDN edge intercepts the origin response, decompresses if necessary, and re-compresses based on the client's Accept-Encoding header. This allows serving Brotli to supporting browsers and gzip to others from the same cached origin response. The edge can also apply compression to responses that the origin didn't compress, such as dynamically generated HTML. The CPU cost of compression at the edge is typically offset by the bandwidth savings, especially for text-based content where Brotli achieves 15-25% better compression ratios than gzip.

Brotli compression levels require careful tuning at CDN edges. Brotli at maximum compression (level 11) produces the smallest output but is CPU-intensive, suitable for static assets during build time. CDN edges typically use Brotli at levels 4-6 for dynamic content, balancing compression ratio against latency. The CDN must also handle edge cases like compressing already-compressed content (images, video), which wastes CPU without benefit. Proper content-type detection and conditional compression logic prevent these inefficiencies.

## Q15: What is origin shielding and why is it used?

**A:** Origin shielding is an architectural pattern where a designated intermediate cache tier (the "shield") sits between edge caches and the origin server. Instead of all edge caches fetching directly from the origin on a cache miss, they fetch from the shield, which itself caches content and fetches from the origin only on its own cache miss. This dramatically reduces the number of connections to the origin, protecting it from load spikes and reducing origin infrastructure costs.

The primary benefit is request collapsing. If 10,000 edge servers simultaneously experience a cache miss for the same popular asset, only the shield (or a small number of shields) makes the origin fetch. The other edges either wait for the shield's response or receive it from the shield's cache once populated. This prevents origin overload during flash crowds, such as when a new product page goes live or a breaking news event drives massive traffic. Origin shielding can reduce origin request volume by 90% or more in typical CDN architectures.

The tradeoff is added latency for cache misses, as the edge must now fetch from the shield rather than the (potentially closer) origin. The shield placement is therefore critical—it should be in a datacenter with low-latency connectivity to the origin and high-bandwidth links to major edge clusters. Many CDNs allow customers to select their shield location or automatically designate one based on traffic patterns. Shielding also adds operational complexity: cache coherence between shield and edge tiers requires consistent invalidation propagation, and a shield failure can temporarily block all origin fetches unless fallback to direct origin access is implemented.

## Q16: How do you ensure high availability in a CDN?

**A:** High availability in a CDN is achieved through redundancy at every layer, from individual servers to entire datacenters. At the server level, multiple instances behind a local load balancer handle traffic, with health checks removing failed nodes from rotation within seconds. Servers are deployed in redundant pairs or N+1 configurations, so a single hardware failure doesn't reduce capacity. Stateless design allows any server to handle any request, simplifying failover and enabling rapid scale-out.

At the datacenter level, each PoP has redundant network paths, power supplies, and uplinks. BGP anycast provides automatic failover: when a datacenter goes offline, its BGP routes are withdrawn, and traffic shifts to the next-closest PoP within the BGP reconvergence time (typically seconds to a few minutes). For faster failover, CDNs use health-check-driven DNS to proactively remove unhealthy PoPs from DNS responses, bypassing BGP reconvergence delays. Multi-homed connectivity (connections to multiple ISPs) ensures that a single ISP failure doesn't isolate a PoP.

At the architecture level, the CDN must handle origin failures gracefully. Stale-if-error caching serves cached content even after expiration if the origin is unreachable, trading freshness for availability. Origin failover uses health checks to detect origin failures and reroute cache-fill traffic to secondary origins. Circuit breakers prevent cascading failures: if origin error rates exceed thresholds, the CDN stops sending traffic to the failing origin and serves cached or degraded responses. Chaos engineering practices (randomly disabling PoPs, origins, or network links) validate that failover mechanisms work correctly under realistic conditions.

## Q17: How is the CAP theorem relevant to CDN design?

**A:** The CAP theorem states that a distributed system can provide at most two of three guarantees: Consistency (all reads return the most recent write), Availability (every request receives a response), and Partition tolerance (the system continues operating despite network partitions). Since network partitions are inevitable in globally distributed systems, the practical choice is between consistency and availability during partitions.

CDNs fundamentally prioritize availability and partition tolerance over strong consistency. A CDN edge may serve stale content when the origin is unreachable or when cache invalidation hasn't propagated to all edges. This is an explicit design choice: users can still access content (availability) even if it's slightly outdated (sacrificing consistency). The consistency model is eventual: after a write or invalidation at the origin, all edges will eventually serve the updated content, but there is a propagation window where different edges may serve different versions.

However, not all CDN use cases are equal in their consistency requirements. Static asset delivery (images, CSS, JavaScript) can tolerate minutes of staleness, making eventual consistency perfectly acceptable. Dynamic content, user-specific data, and transactional operations require stronger guarantees. For these, CDNs use techniques like cache-busting with versioned URLs, short TTLs, and origin-direct access (bypassing cache). Some advanced CDN features implement read-after-write consistency by tagging cache entries with write timestamps and requiring revalidation after detecting a recent write at the origin.

## Q18: How would you monitor CDN performance in production?

**A:** CDN performance monitoring operates at three levels: infrastructure metrics, application metrics, and user experience metrics. Infrastructure monitoring tracks server CPU, memory, disk I/O, network throughput, and error rates at each PoP. SNMP, streaming telemetry (gNMI), and custom agents collect data at sub-minute intervals. Alerting thresholds are set per-PoP to detect anomalies early. Network-layer monitoring includes BGP session stability, packet loss rates, and inter-PoP link utilization, often using tools like BGPStream or ThousandEyes.

Application-level monitoring focuses on cache performance and content delivery quality. Key metrics include cache hit ratio (target >95% for static content), time-to-first-byte (TTFB) distribution, origin fetch latency, error rates by status code, and cache fill bandwidth. These metrics are typically exposed via Prometheus endpoints or CDNs' native dashboards. Distributed tracing (OpenTelemetry) tracks individual requests through the CDN pipeline, identifying bottlenecks in DNS resolution, edge lookup, shield fetch, and origin response.

User experience monitoring uses Real User Measurement (RUM) and synthetic testing. RUM JavaScript on client pages captures actual page load times, Core Web Vitals (LCP, FCP, CLS), and network conditions from real users worldwide. Synthetic testing probes CDN PoPs from strategic locations using tools like Catchpoint or ThousandEyes, providing baseline performance data independent of actual user traffic. Combining RUM and synthetic data allows correlating CDN configuration changes with user-perceived performance impacts, enabling data-driven optimization decisions.

## Q19: What is the difference between horizontal and vertical scaling in network services?

**A:** Vertical scaling (scaling up) involves adding more resources (CPU, RAM, network bandwidth) to existing servers. A single server with a 100Gbps NIC, 512GB RAM, and 128 CPU cores can handle significantly more concurrent connections than a basic server. Vertical scaling is simple: no application changes are needed, and there's no distributed system complexity. However, there are physical limits—a single machine can only be so powerful—and it creates a single point of failure. The cost curve is also unfavorable: doubling performance often costs more than double.

Horizontal scaling (scaling out) involves adding more servers to distribute load. This is the standard approach for network services at scale. A load balancer distributes incoming connections across a pool of servers, each handling a portion of the total load. Horizontal scaling offers near-linear cost scaling, no single point of failure, and the ability to scale beyond any individual machine's limits. The tradeoff is complexity: servers must be stateless (or state must be externally shared), load balancing logic must handle session affinity, and failure detection and auto-scaling infrastructure must be maintained.

Most production CDN and network services use horizontal scaling as the primary strategy with selective vertical scaling for specific components. Edge servers are horizontally scaled by deploying more nodes. However, certain components like DNS authoritative servers, cache coordination services, and configuration management databases may benefit from vertical scaling to avoid distributed consensus complexity. The ideal approach depends on the component's statefulness, latency requirements, and expected growth trajectory.

## Q20: How does connection pooling work in network architecture?

**A:** Connection pooling maintains a set of pre-established network connections that can be reused for subsequent requests, eliminating the overhead of creating new connections for each request. In a CDN or microservices architecture, the edge server maintains a pool of persistent connections to origin servers (or shield caches). When a cache miss requires fetching from origin, the server borrows a connection from the pool, sends the request, receives the response, and returns the connection to the pool rather than closing it.

The pool is configured with parameters for minimum size (warm connections ready for immediate use), maximum size (upper bound to prevent resource exhaustion), idle timeout (how long unused connections remain open), and connection validation (periodic health pings to detect dead connections). TCP connection setup costs (three-way handshake, TLS negotiation) can add 1-3 round trips of latency, so keeping connections warm is critical for performance, especially on high-latency links.

Connection pooling also plays a critical role in HTTP/2 and HTTP/3 multiplexing. A single HTTP/2 connection can carry hundreds of concurrent streams, so the connection pool may only need one or a few connections per origin, dramatically reducing resource usage. However, this creates head-of-line blocking concerns at the transport layer (mitigated by HTTP/3's QUIC). The pool manager must balance connection reuse (amortizing setup costs) against the risk of overloading a single connection or server. Adaptive pool sizing based on measured latency and throughput helps maintain optimal performance.

## Q21: What is the role of load balancers in network system design?

**A:** Load balancers distribute incoming traffic across multiple backend servers to ensure no single server becomes a bottleneck. They operate at multiple layers: L4 (transport layer) load balancers forward TCP/UDP connections based on IP address and port without inspecting application content, offering high performance and low latency. L7 (application layer) load balancers understand HTTP, gRPC, and other application protocols, enabling content-based routing, header manipulation, SSL termination, and request-level health checking.

In modern architectures, load balancers serve as the control plane for traffic management. They implement routing rules (path-based, header-based, canary deployments), rate limiting, circuit breaking, and retries. Service meshes like Istio use sidecar proxies (Envoy) as per-service load balancers, providing fine-grained traffic control within a cluster. Global load balancers (GSLB) extend this across datacenters, using DNS or anycast to direct clients to appropriate regions based on health, latency, and capacity.

Load balancer selection involves tradeoffs between features and performance. Hardware load balancers (F5, A10) offer line-rate performance but are expensive and inflexible. Software load balancers (NGINX, HAProxy, Envoy) provide flexibility and run on commodity hardware. Cloud-native load balancers (AWS ALB/NLB, GCP Cloud Load Balancing) abstract infrastructure management. Modern designs increasingly use kernel-bypass techniques (DPDK, XDP) to achieve hardware-like performance in software load balancers, enabling millions of new connections per second with microsecond-level latency.

## Q22: How do health checks work for backend servers?

**A:** Health checks are periodic probes that verify whether backend servers are capable of handling traffic. They operate at multiple levels. TCP health checks verify that the server is listening on the expected port and accepting connections. HTTP health checks send a request to a dedicated health endpoint and verify that the response status code is in the 2xx range. Application-level health checks may verify database connectivity, cache availability, or dependency health, ensuring the server can actually serve real requests, not just accept TCP connections.

Health checks are configured with parameters for interval (how often to probe), timeout (how long to wait for a response), healthy threshold (number of consecutive successes before marking a server healthy), and unhealthy threshold (number of failures before removing from rotation). Aggressive settings (short interval, low unhealthy threshold) detect failures quickly but risk false positives. Conservative settings reduce false positives but delay failover. Most systems use asymmetric thresholds: quick to remove (2-3 failures) but slower to add back (5-10 successes) to avoid flapping.

Advanced health checking integrates with circuit breaker patterns. Instead of binary healthy/unhealthy states, the system tracks error rates, latency percentiles, and connection success rates. A server with a 5% error rate might be flagged as "degraded" and receive reduced traffic rather than being completely removed. Active health checks (synthetic requests) complement passive health checks (real traffic monitoring), providing coverage for scenarios where real traffic is too low to trigger failures. In distributed systems, health check aggregation across multiple vantage points prevents a single network partition from incorrectly marking healthy servers as failed.

## Q23: What is consistent hashing and where is it used?

**A:** Consistent hashing is a technique that maps both servers and keys onto a hash ring, minimizing the number of keys that need to be remapped when servers are added or removed. In naive modulo-N hashing, adding or removing a server changes the hash modulus, causing almost all keys to map to different servers—a catastrophic redistribution. Consistent hashing ensures that adding or removing a server only affects approximately 1/N of the keys, where N is the number of servers. This property is critical for distributed caches, CDNs, and distributed databases.

The hash ring is constructed by hashing both server identifiers and keys using the same hash function (like SHA-256). A key is assigned to the first server encountered when traversing the ring clockwise from the key's hash position. Virtual nodes (vnodes) are used to improve load distribution: each physical server is assigned multiple positions on the ring, spreading its load more evenly. Without virtual nodes, keys can cluster around a small number of physical nodes, creating hotspots. With sufficient virtual nodes (typically 100-200 per physical server), load distribution approaches uniform.

Consistent hashing is used extensively in distributed caches (Memcached, Redis Cluster), CDNs (routing requests to edge servers), distributed databases (Cassandra, DynamoDB partition assignment), and load balancers (session affinity). In CDNs, consistent hashing determines which edge server within a PoP stores a particular cached asset, enabling efficient cache distribution without centralized coordination. When an edge server fails, its keys are redistributed to neighboring servers on the ring, and only the affected fraction of cache entries needs to be re-fetched from the origin.

## Q24: How does DNS failover work for high-availability architectures?

**A:** DNS failover is the process of automatically updating DNS records to redirect traffic away from failed servers or datacenters. The basic mechanism involves health-checking backend resources and updating DNS records when failures are detected. When a primary server or datacenter fails health checks, its DNS records are removed or updated to point to a secondary location. Clients resolving the domain receive the updated IP addresses, directing them to healthy backends.

The challenge is TTL propagation. DNS responses are cached at recursive resolvers, ISP caches, and client stubs for the duration of the TTL. Even after updating the authoritative DNS, clients using cached records continue connecting to the failed endpoint until the cache expires. Short TTLs (30-60 seconds) minimize failover delay but increase DNS query volume and cost. Long TTLs reduce DNS load but delay failover. Many architectures use short TTLs (60s) for the primary record while using longer TTLs for backup records, balancing failover speed against DNS infrastructure cost.

Advanced DNS failover integrates with traffic management systems. Global server load balancing (GSLB) combines DNS with health checking, latency measurement, and traffic steering policies. Instead of simple failover, GSLB can implement weighted routing (sending 90% of traffic to primary, 10% to secondary), latency-based routing (directing each client to the lowest-latency backend), and automatic scaling (adding new DNS entries as capacity scales up). Health checks run from multiple geographic locations to avoid false positives from localized network issues. The failover sequence typically involves DNS updates, BGP route advertisements, and application-layer redirects, layered to provide both coarse and fine-grained traffic management.

## Q25: What are the tradeoffs between UDP and TCP for real-time applications?

**A:** TCP provides reliable, ordered delivery through connection management, acknowledgments, retransmissions, and flow control. This makes it ideal for web browsing, file transfer, and API calls where data integrity is paramount. However, TCP's reliability mechanisms introduce latency: retransmitted packets wait in the send queue, head-of-line blocking delays subsequent data, and congestion control throttles throughput during loss events. For real-time applications like video conferencing, live gaming, and VoIP, this latency is more damaging than occasional packet loss.

UDP provides lightweight, best-effort delivery without connection establishment, acknowledgments, or retransmissions. This makes UDP ideal for real-time media where low latency is critical and some packet loss is acceptable. WebRTC uses UDP as its transport, implementing application-level reliability where needed (e.g., retransmitting keyframes but not every video frame). DNS, DHCP, and NTP also use UDP for their request-response patterns where the overhead of TCP's three-way handshake is disproportionate to the payload.

The tradeoff is between reliability and latency. TCP adds 1-3 round trips of connection setup latency, and retransmission of lost packets delays all subsequent data in the stream (head-of-line blocking). UDP avoids this overhead but requires the application to handle loss, ordering, and congestion control. Modern protocols like QUIC (used by HTTP/3) implement reliability and congestion control over UDP, combining UDP's flexibility with TCP-like guarantees while avoiding head-of-line blocking through per-stream multiplexing. For real-time applications, the choice depends on whether the application can tolerate loss (UDP) or requires perfect delivery (TCP).

The system dynamically adjusts shaping parameters based on link utilization, measuring actual throughput against allocated bandwidth and redistributing unused capacity from low-priority to high-priority classes.

The system must handle congestion events (link failures, traffic spikes) without dropping high-priority traffic. Active Queue Management (AQM) algorithms (CoDel, PIE) manage bufferbloat by detecting and controlling persistent queue buildup. For global backbone links, the system implements traffic engineering (MPLS-TE, Segment Routing) to distribute traffic across multiple paths based on real-time link utilization and latency measurements. The control plane continuously monitors traffic patterns and adjusts shaping policies, balancing throughput, latency, and fairness across competing applications and tenants.

## Q85: How would you design a global API versioning strategy for backward compatibility?

**A:** A global API versioning strategy balances delivering new features against preserving compatibility for existing clients. The strategy uses URI path versioning (`/v1/...`, `/v2/...`) as the primary mechanism, since it is explicit, discoverable, and trivially cacheable. Header-based versioning (`Accept: application/vnd.service+json;version=2`) and query parameter versioning are alternatives that keep the URL stable, but they complicate caching and discovery. Each version is deployed as an independent service or container, managed by the API gateway's routing configuration.

Backward compatibility rules preserve the explicit contract across versions: existing fields must never be removed or have their types changed; new fields are added to responses incrementally (clients reading unknown fields must ignore them); new endpoint parameters are optional with default behavior matching the prior version. Breaking changes (removing a field, changing semantics, changing error codes) always require a new version. The versioning policy defines deprecation timelines: a version is deprecated with advanced notice, supported through a sunset period (e.g., 12 months), and then removed. The API returns `Sunset` and `Deprecation` headers on all responses from deprecated versions, indicating the end-of-life date and migration path.

The strategy includes version-specific analytics and migration tooling: usage tracking identifies which clients still use deprecated versions, enabling targeted migration outreach; comparison tooling validates that v2 endpoint responses match v1 responses for the same logical operation where behavior should be unchanged. A contract testing suite (OpenAPI schemas, Pact-style consumer-driven contracts) verifies that changes do not silently break consumer expectations. The gateway enforces versioning rules: requests to removed versions receive HTTP 410 Gone with guidance; requests to deprecated versions receive warnings in headers. Cross-version shared code is managed via versioned modules, ensuring implementations of different versions coexist safely.

## Q86: How would you design a global Redis/Memcached caching layer for microservices?

**A:** A global caching layer for microservices uses a Redis Cluster and/or Memcached deployed across regions, providing fast, in-memory data access between services. The architecture uses two tiers: a L1 cache (per-instance, in-process) and a L2 cache (distributed, per-region Redis Cluster). L1 caches are extremely fast (microsecond access) but logically local; L2 caches provide millisecond access and shared data across instances within a region. Read paths check L1, then L2, then the source of truth (database or service call). Write paths update the source, then invalidate or update L2 and L1 accordingly.

Data models for caching vary by access pattern: cache-aside for unpredictable reads (load data into cache on miss), write-through for consistent reads (update cache on write), write-behind for high write throughput (async update to source), and proactive TTL-based refresh for known-hot data. Cache eviction policies (LRU, LFU, ARC) manage memory: the cache stores the most-valued data based on access frequency, recency, and load cost. Cache keys are designed with invalidation in mind: logical keys (`user:{id}:profile`) support targeted invalidation; tag-based keys (`product:{id};category:{electronics}`) support group invalidation.

The global layer addresses cross-region data access: hot data replicated across regions via Redis's cross-region replication or an application-side write-through pattern; region-local data stays in its region. Cache stampedes and thundering herd protection use locking (setnx), probabilistic early expiration (XFetch), and stale-while-revalidate. Cache node failures must be tolerated: consistent hashing distributes keys across nodes so a node loss only affects 1/N of keys; the cache layer falls back to source-of-truth on cache misses. Observability tracks hit ratio, latency percentiles, eviction rate, and memory utilization per cache tier, per region. Cost optimization balances cache size against source-of-truth load and latency.
