# Revenue Metrics

## Overview

Revenue metrics quantify the financial impact of recommendation systems. While accuracy and engagement metrics are important for model development, revenue metrics answer the fundamental business question: do recommendations make money? In production systems, revenue metrics ultimately determine whether a recommendation system receives continued investment and engineering resources.

## Revenue per Recommendation

### Definition

```
Revenue per Recommendation (RPR) = Total Revenue Attributed to Recommendations / Total Recommendation Impressions
```

### Micro RPR (Per-Item)

```
Micro_RPR(i) = Revenue Generated by Item i / Times Item i Was Recommended
```

### Macro RPR (Per-List)

```
Macro_RPR(session) = Revenue Generated in Session / Number of Recommendation Lists Shown
```

### RPR by Recommendation Type

| Rec Type | Typical RPR | Why |
|----------|------------|-----|
| "Because you purchased X" | High | Strong purchase intent |
| "Trending now" | Medium | Social proof, moderate intent |
| "New arrivals" | Low–Medium | Discovery, low immediate intent |
| "People also bought" | High | Cross-sell, complementary items |
| "For you" (personalized) | Medium–High | Depends on personalization quality |

### RPR Optimization Strategies
1. **Price-aware ranking**: Rank by expected revenue, not just relevance
2. **Margin-aware ranking**: Consider profit margin, not just revenue
3. **Inventory-aware ranking**: Prioritize items with high stock levels to avoid dead inventory
4. **Dynamic pricing integration**: Adjust recommendations based on price sensitivity

## Revenue per User

### Definition

```
Revenue per User (RPU) = Total Revenue / Total Active Users
```

### RPU Segmentation

| Segment | RPU Calculation | Insight |
|---------|----------------|---------|
| By recommendation engagement | RPU(users who click recs) vs RPU(users who don't) | Incremental value of recommendations |
| By user tenure | RPU by month-since-registration | Lifetime value trajectory |
| By acquisition channel | RPU by source | Channel ROI comparison |
| By device | RPU mobile vs desktop | Platform monetization differences |

### RPU Decomposition

```
RPU = Conversion_Rate × Average_Order_Value × Orders_per_User
```

Each component can be independently optimized:
- **Conversion rate**: Improve recommendation relevance
- **AOV**: Recommend complementary/higher-value items
- **Orders per user**: Improve retention and session frequency

## Average Order Value (AOV)

### Definition

```
AOV = Total Revenue / Total Orders
```

### AOV and Recommendations

| Recommendation Strategy | AOV Impact | Mechanism |
|------------------------|-----------|-----------|
| Cross-sell (complementary items) | ↑ 10–25% | Add accessories, refills, related items |
| Upsell (higher-tier items) | ↑ 15–30% | Recommend premium versions |
| Bundle recommendations | ↑ 20–40% | Suggest item combinations |
| Free-shipping threshold | ↑ 5–15% | "Add X more for free shipping" |
| Personalized AOV targeting | ↑ 10–20% | Match recommendation price to user willingness to pay |

### AOV Segmentation

```
AOV_by_segment = Revenue(segment) / Orders(segment)
```

Compare AOV across:
- Recommendation-exposed vs. non-exposed users
- Users who clicked recommendations vs. those who didn't
- Different recommendation algorithms

## Revenue Attribution to Recommendations

### Attribution Approaches

| Method | Formula | Pros | Cons |
|--------|---------|------|------|
| **Direct attribution** | Revenue from items clicked from recs | Simple, conservative | Ignores view-through, halo effects |
| **View-through attribution** | Revenue from items shown in recs (even if not clicked) | Captures awareness | Over-attributes |
| **Incrementality** | Revenue(treatment) - Revenue(control) | Causal estimate | Requires A/B test |
| **Shapley value** | Marginal contribution of rec channel | Fair multi-touch | Complex to compute |

### Incrementality Measurement

The gold standard for revenue attribution is incrementality—the additional revenue caused by recommendations:

```
Incremental_Revenue = Revenue_with_Recommendations - Revenue_without_Recommendations
```

This requires a holdout group that receives no recommendations (or generic ones). The incremental revenue per user:

```
IRPU = (RPU_treatment - RPU_control)
```

### Revenue Lift Calculation

```
Revenue_Lift% = (IRPU / RPU_control) × 100
```

Typical revenue lifts:
- **Good recommendation system**: 5–15% incremental revenue
- **Excellent recommendation system**: 15–30% incremental revenue
- **Transformative**: >30% (rare; often involves new recommendation surfaces)

### Attribution Windows for Revenue

| Window | Use Case | Consideration |
|--------|---------|---------------|
| Same-session | Impulse purchases | Conservative; misses delayed purchases |
| 24-hour | Daily shopping cycles | Standard for most e-commerce |
| 7-day | Considered purchases | Captures multi-day decision cycles |
| 30-day | High-value items | Captures research-heavy purchases |
| Custom | Product-specific | Based on purchase delay distribution |

## Customer Lifetime Value (CLV)

### Definition

```
CLV = Σ (t=0 to T) [Revenue_t × Discount_Factor_t] - Acquisition_Cost
```

### CLV and Recommendations

| CLV Component | Recommendation Impact | Measurement |
|--------------|----------------------|-------------|
| **Purchase frequency** | Better recs → more frequent purchases | Orders per user over time |
| **Average order value** | Cross-sell/upsell recs → higher AOV | AOV for rec-engaged users |
| **Retention rate** | Good recs → longer customer lifespan | Churn rate reduction |
| **Acquisition cost** | Rec-driven word-of-mouth → lower CAC | Referral rate by rec-engaged users |

### CLV Prediction Models

| Model | Complexity | Data Requirements | Accuracy |
|-------|-----------|------------------|----------|
| Historical CLV | Low | Past purchase data | Low |
| BG/NBD model | Medium | Transaction frequency + recency | Good |
| Pareto/NBD | Medium | Transaction patterns | Good |
| Deep learning CLV | High | Full behavioral sequence | Best |

### Recommendation-Driven CLV Lift

```
CLV_Lift = (CLV_rec_users - CLV_non_rec_users) / CLV_non_rec_users × 100%
```

This is the long-term revenue impact of recommendations, often much larger than short-term revenue metrics suggest.

## Incremental Revenue (Causal Impact)

### Why Incrementality Matters

Not all revenue attributed to recommendations is truly caused by them:
- **Organic purchases**: Users would have bought the item anyway
- **Halo effect**: Recommendations increase overall browsing, which increases all purchases
- **Selection bias**: Users who engage with recommendations are already more engaged

### Causal Impact Methods

#### A/B Testing (Gold Standard)
- Randomly assign users to treatment (personalized recs) and control (non-personalized)
- Measure revenue difference between groups
- Clean, interpretable, but requires sufficient sample size

#### Difference-in-Differences
```
Causal_Impact = (Rev_treatment_after - Rev_treatment_before) - (Rev_control_after - Rev_control_before)
```
- Controls for time-varying confounders
- Requires parallel trends assumption

#### Regression Discontinuity
- Exploit a threshold in recommendation eligibility
- Compare users just above and below the threshold
- Valid when the threshold is arbitrary

#### Instrumental Variables
- Find an instrument that affects recommendation exposure but not revenue directly
- Example: Server load or random UI variations

### Incrementality Reporting

| Metric | Formula | Interpretation |
|--------|---------|---------------|
| Incremental revenue per user | RPU_treatment - RPU_control | Absolute lift |
| Incremental revenue ratio | (RPU_treatment - RPU_control) / RPU_control | Relative lift |
| Recommendation-attributed revenue share | Revenue_recs / Total_revenue | System's contribution |
| Organic cannibalization rate | 1 - Incremental / Attributed | Over-estimation factor |

### Common Revenue Measurement Mistakes

1. **Using attributed revenue as causal revenue**: Attributed revenue overestimates true impact
2. **Ignoring cannibalization**: Recommendations may shift purchases from one item to another without increasing total revenue
3. **Short measurement windows**: Revenue impact often lags engagement impact
4. **Ignoring costs**: A recommendation system with high infrastructure costs may not be profitable even with revenue lift
5. **Survivorship bias**: Only measuring revenue for retained users ignores the impact of recommendations on retention
