# Adapting To The Live Format

> Section 00 · Exam Blueprint · Pretest History And Variants · _Estimated reading time: 14 min_
> **Prerequisite:** [../01-concepts/03-what-stays-constant.md](../01-concepts/03-what-stays-constant.md)

## In one sentence
**Spend the first two minutes reading the live instructions and re-planning your time budgets to the actual sections — not the ones you expected.**

## Why the pre-test tests this
- **Variance is normal:** counts, order, and penalties change between batches.
- **Fast adaptation preserves marks.**
- **Rigid plans break** when the format differs from expectation.
- **The 90-second rule survives any format**, so it is the anchor to fall back on.

## Core concept

### The 2-minute live-config procedure
| Time | Action | Output |
|------|--------|--------|
| 0:00-0:30 | Read all instructions | Note penalty, marks per question, section list |
| 0:30-1:00 | Count sections and questions | Note actual counts vs expected |
| 1:00-1:30 | Identify the largest section | Note what to protect |
| 1:30-2:00 | Set rough budgets | Seconds per question per section |
| 2:00+ | Start with cheap marks | Execute the 90-second rule |

### The re-planning formula
```
seconds_per_question(section) = section_minutes × 60 / section_questions
```
Keep the global rate at roughly 0.667 questions per minute.

### The re-budget worked table
| Section | Count | Assigned minutes | Seconds/Q |
|---------|-------|------------------|-----------|
| Aptitude | 12 | 16 | 80 |
| English & L&D | 13 | 20 | 92 |
| DBMS / SQL | 8 | 14 | 105 |
| Java | 25 | 34 | 82 |
| **Total** | **58** | **84** | +6 min review |

### If the format differs from expectation
| Difference | Adjustment |
|-----------|-----------|
| Java smaller than expected | Move freed time to the largest remaining section |
| A section missing (e.g., no DBMS) | Redirect its budget to English or Java |
| Order changed | Attack by solvability, not the listed order |
| Negative marking present | Apply the net-score rule and elimination-based guessing |
| Coding round instead of MCQ | Do compile/output questions you recognise first |

## Worked example
**Rahul expects 10/15/10/25** but the live test is 12/13/10/25 with Java first and a `+0/−0.25` penalty.

1. He notes the penalty → he will only guess with eliminations.
2. He sees Java first (his strength) → attacks it immediately.
3. He re-budgets the slightly larger Aptitude to 16 minutes and trims his review slightly.
4. He uses the 90-second rule throughout.

**Result:** no time lost to surprise; the plan matched the live test within two minutes.

### What to write on your rough sheet
| Item | Example |
|------|---------|
| Penalty | −0.25 per wrong |
| Counts | 12 / 13 / 10 / 25 |
| Largest section | Java (25) |
| Budgets | 16 / 20 / 14 / 34 min |
| Guess rule | Eliminate two, then guess |

## Quick rules
- **The first two minutes are live config.**
- **Re-budget to the actual counts.**
- **Keep the global rate around 0.667 questions per minute.**
- **Protect the largest section.**
- **Match the live penalty policy.**
- **Attack by solvability if the order changed.**

## Common traps
- **Starting questions before reading the instructions.**
- **Sticking to the expected format** despite the live one differing.
- **Missing the negative-marking line.**
- **Not re-budgeting when the counts change.**

## Checklist
- [ ] You run the 2-minute live-config procedure.
- [ ] You note the penalty on your rough sheet.
- [ ] You re-budget to the actual counts.
- [ ] You protect the largest section.
- [ ] You keep the global rate.
- [ ] You attack by solvability.
